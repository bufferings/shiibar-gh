# M2: GitHub の取得とトークン

Status: 完了

最初に CLAUDE.md、docs/DESIGN.md、docs/DEVELOPMENT.md、docs/tasks/M1.md を確認すること。挙動の正は DESIGN.md である。指示書と DESIGN.md が食い違う場合は、実装を止めてオーケストレーターに報告する。

## ゴール

登録したトークンでデーモンが GitHub から PR と出来事を取得し、M1 の `Ingest` に変換して中核へ渡す。`shiibar-gh token set` でトークンを登録すると、`list`、`activity`、通知が実際の GitHub の内容で DESIGN.md のとおりに動作する。テストは GitHub と Keychain に触れずに、偽の GitHub と偽の Keychain で同じ処理を確認する。

## 範囲

### 含める

- REST の Notifications API のポーリング（If-Modified-Since と X-Poll-Interval）
- GraphQL の search による対象 PR の発見、`nodes(ids:)` による状況の取得、timelineItems による出来事の取得、レビュースレッドの取得、Reaction の取得、`repository(owner, name){ pullRequest(number){ id } }` による id の解決
- REST の GitHub Actions（workflow run と job）による失敗したチェックの名前の取得
- チームの所属の取得と、チーム宛てのレビュー依頼とチームへのメンションの判定。Public のチーム宛ての依頼の、通知用の classic PAT による読み直し
- GitHub の値から `Ingest` への変換。状況アイコンの値、行の kind、Bot、自分の投稿、本文のリンクによるメンションの判定を含む
- 監視期間（カードが消えてから Days to keep watching after close の間）の判定と、その結果による取得対象の決定と `watching` の値
- レート制限：`rateLimit` の確認、GraphQL cost cap の 80% の警告、上限による停止と再開、REST と GraphQL の残量の保持、二次レート制限の待機
- 取得の失敗の扱いと再試行、スコープの `warnings`。`warnings` の要素の型を文字列からオブジェクトに変更する
- Keychain：トークンの保存、読み取り、削除。Keychain に触れるのはデーモンだけ
- ワイヤ形式の `token_set` と `token_test`、CLI の `token set` と `token test`（`notifications`、`public`、owner）。CLI はトークンを標準入力から読み取る
- 設定画面の値を返す要求（「警告とワイヤ形式」）
- スコープの kind（`org`、`user`）の解決
- `refresh` の実際の取得。`reset` のあとに Keychain のトークンからスコープを復元する処理（DESIGN.md の「DB を読めないとき」）。scope remove での Keychain のトークンの削除
- 中核の変更：取得に成功したスコープの Updated … ago の更新、通知のまとめ方（DESIGN.md の「macOS 通知」）、Reaction の基準値、Include requests to my teams の扱い、今も続くレビュー依頼の行（DESIGN.md の「監視開始より前の出来事」）、手動の Unsnooze で Snooze より前の未配信の通知の記録を消去する修正（M1 の中核の unsnooze の処理。`HeldUndelivered` も `Held` と同じく通知の予定をなくす）
- `Ingest` の拡張。省略可能なフィールド（取得に成功したスコープの一覧、レビュー依頼の自分宛てとチーム宛ての区別）を追加する。`dev_ingest` も同じ型を使用し、取得処理は `dev_ingest` と同じ `Ingest` を中核へ渡す（「取得と中核の分担」）

### 含めない

- Swift アプリ、署名、リリース。設定画面の「Before your changes」（変更前のコスト）、「Repositories: all」、伏せ字のトークンの表示（M3 で扱う）
- GitHub への書き込み。既読の同期、コメント、レビューを含めて一切行わない。Notifications API の既読化の操作も呼び出さない

## 確定事項

ここに記載する事項は、DESIGN.md の記述、所有者の決定、または確認した外部仕様から決まる。外部仕様の確認方法は各項目と「確認した外部仕様」に記載する。

### 取得の構成

| 取得 | トークン | API | 契機 |
| --- | --- | --- | --- |
| 更新された PR の検知 | 通知用の classic PAT | REST `GET /notifications`（`all=true`、`per_page=50`、`since` は前回の最新）。前回の `Last-Modified` をそのまま `If-Modified-Since` に渡し、`X-Poll-Interval` の秒数より短い間隔で呼び出さない | `X-Poll-Interval` |
| 対象 PR の発見 | スコープのトークン（Public は Public の fine-grained PAT） | GraphQL `search(type: ISSUE)`。検索条件は下に記載 | PR status interval |
| 状況アイコン、状態ラベル | 同上 | GraphQL `nodes(ids:)`。100 件ずつに分割する | PR status interval |
| 失敗したチェックの名前 | 同上 | REST `GET /repos/{owner}/{repo}/actions/runs?head_sha=` と `GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs` | 状況の取得で Checks が `failed` のとき |
| 出来事 | 同上 | 更新された PR の GraphQL `timelineItems(since:, itemTypes:)` | 通知、または状況の取得で `updatedAt` の変化を検知したとき |
| Reply | 同上 | 記録したレビュースレッドの id を `nodes(ids:)` で取得し、スレッドのコメントを参照する | 出来事と同じ |
| 自分のコメントへの Reaction | 同上 | 記録した自分のコメント、レビュー、レビューコメント、PR の id を `nodes(ids:)` で 100 件ずつ取得し、`reactionGroups` を参照する | Reactions interval |
| チームの所属 | owner のスコープはスコープのトークン（Members: Read）。Public は通知用の classic PAT（`read:org`） | GraphQL `organization.teams(userLogins:)`、または REST `GET /user/teams` | 取得処理が決める |
| Public のチーム宛てのレビュー依頼 | 通知用の classic PAT | Public の fine-grained PAT で `requestedReviewer` が `null` だった PR の `reviewRequests` と REVIEW_REQUESTED_EVENT を読み直す | その PR を取得したとき |
| PR の id の解決 | スコープのトークン | GraphQL `repository(owner, name){ pullRequest(number){ id } }` | 通知で初めて検出した PR |

- Notifications API は classic PAT の認証だけを受け付ける。fine-grained PAT で呼び出すと 403（`Resource not accessible by personal access token`）が返る。確認：docs.github.com/en/rest/activity/notifications の冒頭の注記と、所有者の確認（2026-11-03）
- 通知の `reason` は行の種類の判定に使用せず、再取得の合図としてだけ使用する（DESIGN.md の「reason を判定に使用しない理由」）。チームへのメンションの通知（reason `team_mention`）も、タイムラインを取得する合図として扱う
- 通知が 50 件を超えるときは、応答の `Link` ヘッダーの `next` で次のページを取得する
- `since` を変更しながら `If-Modified-Since` を渡したときの応答は確認していない。200 が返れば通常の応答として扱う
- 変更がなければ 304 を返し、レート制限を消費しない。確認：同ページの「About GitHub notifications」と、所有者の確認（`X-Poll-Interval` は 60。前回の `Last-Modified` を `If-Modified-Since` に渡すと 304）
- PR の通知のスレッドは、`subject.type` が `PullRequest`、`subject.url` が `https://api.github.com/repos/{owner}/{repo}/pulls/{number}` である。確認：所有者の確認（2026-11-03）
- `nodes(ids:)` は 100 件まで受け付ける。101 件では `ARGUMENT_LIMIT`（`You may not provide more than 100 node ids`）で `data` が `null` になる。存在しない id と不正な形式の id は、その要素が `null` になり、`NOT_FOUND` のエラーが付き、ほかの要素は返る。HTTP は 200 である。取得処理は `null` の要素の id を `missing_pr_ids` に含める。確認：所有者の確認（2026-11-03）
- GraphQL は認証が必須である。確認：docs.github.com/en/rest/search/search の「Search users」の注記
- 1 回の GraphQL 呼び出しで、connection には `first` または `last`（1 から 100）が必要である。確認：docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api の「Node limit」
- 取得の要求は同時に実行せず、順に実行する。ドキュメントは同時の要求を避けるよう推奨している（同ページの「Staying under the rate limit」）

### 対象 PR の検索

スコープごとに次の 4 つを、PR status interval ごとに、エイリアスを使用した 1 回の GraphQL の要求で検索し、結果を PR の id で重複を除いてまとめる。4 つの検索（`first:100`、`nodes{id}`）を 1 回の要求にまとめたときの `rateLimit.cost` は 1 だった（確認：2026-11-05 に gh で実行）。100 件を超える検索は `pageInfo.endCursor` と `after` で次のページを取得する。D は Days without updates before a PR is dropped の日数前の日付である。

- `is:pr is:open involves:@me updated:>=D`
- `is:pr is:open reviewed-by:@me updated:>=D`
- `is:pr is:open author:@me`
- `is:pr is:open review-requested:@me`。Include requests to my teams がオフなら `is:pr is:open user-review-requested:@me`。オンに戻したあとに見つかった PR のオフの間の依頼は、既読で表示し、さかのぼって通知しない（DESIGN.md の「Include requests to my teams」）。中核は設定を最後にオンにした時刻を保存し、それより前に作成されたチーム宛ての REVIEW_REQUESTED_EVENT をこの扱いにする。確認：search の修飾子のドキュメント（`review-requested` は自分が属するチームへの依頼を含み、`user-review-requested` は自分への直接の依頼だけを含む。段階 1 のレビューで確認）

owner のスコープは、kind に合わせて `org:<owner>` または `user:<owner>` を加える。Public は `is:public` を加え、登録済みの owner の PR を結果から除く。閉じた PR と、更新のない他の人の PR は、通知と状況の取得で追跡する。`involves` はレビューした人を含まないので、`reviewed-by` を別に検索する。確認：docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests。所有者の確認では、`reviewed-by:@me` の 28 件が `involves:@me` の上位の結果に現れなかった

### PR の値

`Ingest` の PR の値は次の GraphQL のフィールドから求める。型と値の一覧は公開スキーマで確認した。

| `Ingest` | GraphQL | 変換 |
| --- | --- | --- |
| `id`、`number`、`url`、`title` | `id`、`number`、`url`、`title` | |
| `owner`、`repo` | `repository.owner.login`、`repository.name` | GitHub が返す表記で保存する |
| `author` | `author.login` | `author` は `Actor` で `null` を許容する。`null` なら空文字列とし、自分の PR とはみなさない |
| `base`、`head` | `baseRefName`、`headRefName` | |
| `state` | `state`（`OPEN`、`CLOSED`、`MERGED`） | 小文字に変換する |
| `is_draft` | `isDraft` | |
| `review` | `reviewDecision`（`APPROVED`、`CHANGES_REQUESTED`、`REVIEW_REQUIRED`、`null`） | `null` なら `latestOpinionatedReviews` から求める。`CHANGES_REQUESTED` が 1 件でもあれば `changes_requested`、なければ `APPROVED` が 1 件でもあれば `approved`、どちらもなければ `none` |
| `checks` | `statusCheckRollup.state`（`StatusState`：`ERROR`、`EXPECTED`、`FAILURE`、`PENDING`、`SUCCESS`。`statusCheckRollup` 自体が `null` を許容する） | `SUCCESS` → `passed`、`PENDING` と `EXPECTED` → `in_progress`、`FAILURE` と `ERROR` → `failed`、`null` → `none` |
| `base_status` | `mergeable`（`CONFLICTING`、`MERGEABLE`、`UNKNOWN`）と `baseRef.compare(headRef:).behindBy` | `CONFLICTING` なら `conflicts`。`behindBy` が 1 以上なら `behind`、0 なら `up_to_date`。`behindBy` を取得できなければ `conflicts` または `none`（空欄）。`mergeable` が `UNKNOWN` なら、`base_status` と `mergeable` の両方で前回の値を保つ。初めて検出した PR で `UNKNOWN` なら、`base_status` は `none`（空欄）、`mergeable` は偽にする |
| `mergeable` | `mergeStateStatus == CLEAN` | 自前で計算しない（DESIGN.md の「状況アイコン 3 つ」） |
| `failed_check` | 下の「失敗したチェックの名前」 | |
| `changes_requested_by` | `latestOpinionatedReviews` のうち `state` が `CHANGES_REQUESTED` のレビューの `author.login` | 最初のレビュアーのログイン名と、残りの数（`+N`） |
| `updated_at` | `updatedAt` | |
| `is_private` | `repository.isPrivate` | |
| `requested_me` | `reviewRequests` の `requestedReviewer` が自分、または自分が属するチーム | `RequestedReviewer` は `Bot`、`EnterpriseTeam`、`Mannequin`、`Team`、`User` の union である。自分宛てとチーム宛てを区別して中核へ渡し、Include requests to my teams は中核が適用する |
| `links` | PR の URL から求める | `review` と `base` は PR の URL、`checks` は `<PR の URL>/checks` |

`mergeStateStatus` の `DRAFT` は非推奨で、`isDraft` を使用する。確認：公開スキーマの `MergeStateStatus`。

fine-grained PAT で読める値は、権限ごとに次のとおりである。確認：所有者が非公開の PR で権限を 1 つずつ追加して確認した（2026-11-03）。

| 権限 | 取得できる値 |
| --- | --- |
| Pull requests: Read だけ | 基本のフィールド、レビュー、タイムライン。`statusCheckRollup` と `baseRef` は FORBIDDEN |
| ＋ Contents: Read | `compare` の `behindBy`（GraphQL と REST） |
| ＋ Commit statuses: Read | `statusCheckRollup.state` と `contexts.totalCount`。CheckRun の要素はすべて FORBIDDEN |

fine-grained PAT には Checks の権限がない。REST の check-runs は 403（`x-accepted-github-permissions: checks=read`）を返す。そのため、owner のスコープのトークンの権限は Pull requests、Commit statuses、Contents、Actions（いずれも Read）と Metadata、org では Members: Read とする（DESIGN.md の「fine-grained PAT の権限」）。

### 失敗したチェックの名前

- PR の head のコミットの workflow run を `actions/runs?head_sha=` で求め、各 run の job を `actions/runs/{run_id}/jobs` で求める。job の名前を先に、次に `statusCheckRollup.contexts` の `StatusContext.context` を候補にする
- 失敗は、完了した job のうち `conclusion` が success、neutral、skipped 以外のものと、`state` が `FAILURE` または `ERROR` の StatusContext である。完了していない job（`conclusion` が `null`）と、`PENDING` または `EXPECTED` の StatusContext は失敗に含めない
- `statusCheckRollup` に含まれない run（Copilot のレビューなど、`event` が `dynamic` の run）は除く
- 本文は最初の名前と、残りの数（`+N`）とする。どちらからも名前を取得できなければ `null` にする
- 確認：fine-grained PAT の権限は docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens の「Repository permissions for "Actions"」に、両方の endpoint が read として記載されている（2026-11-05）。`head_sha` が workflow run の一覧の引数であることは docs.github.com/en/rest/actions/workflow-runs、job の `conclusion` の値（`success`、`failure`、`neutral`、`cancelled`、`skipped`、`timed_out`、`action_required`、`null`）は docs.github.com/en/rest/actions/workflow-jobs で確認した

### 出来事の kind

timelineItems の itemTypes に指定する値と、DESIGN.md の「Needs action の判定」の対応は次のとおりである。itemTypes の値はすべて公開スキーマの `PullRequestTimelineItemsItemType` にある。

| kind | 取得元 | 判定 |
| --- | --- | --- |
| `review_requested` | `REVIEW_REQUESTED_EVENT` | `requestedReviewer` が自分、または自分が属するチーム。チーム宛ては設定に関係なく記録し、チーム宛てであることを中核へ渡す |
| `mentioned` | `bodyHTML` の自分への `user-mention` のリンク、または自分が属するチームへの `team-mention` のリンク | 自分以外の投稿。下に記載 |
| `comment` | 自分の PR の `ISSUE_COMMENT`、レビューの本文、インラインコメント | `author` が Bot でも自分でもない。1 コメントにつき 1 行。Approve のレビューの本文も含む。本文のないレビューは行にしない |
| `bot_comment` | 自分の PR の `ISSUE_COMMENT`、レビューの本文、インラインコメント。記録したスレッドへの Bot の返信と、自分をメンションした Bot の投稿 | `author` の型が `Bot` である。Bot comments の設定に従い、Needs action にしない。`reply` と `mentioned` にしない |
| `reply` | 記録したレビュースレッドのコメント | 下に記載 |
| `merged`、`closed` | `MERGED_EVENT`、`CLOSED_EVENT` | 自分の操作かは問わない |
| `added_to_merge_queue`、`removed_from_merge_queue` | `ADDED_TO_MERGE_QUEUE_EVENT`、`REMOVED_FROM_MERGE_QUEUE_EVENT` | `reason` が `merged` の REMOVED_FROM_MERGE_QUEUE_EVENT は行にしない |

- 他の人の PR の会話のコメントは行にしない。参加の判定は使用しない
- 本文付きで変更を求めるレビューは、状態変化の Changes requested と、`comment` の両方を生成する
- Bot の判定は `author` の `__typename` が `Bot` であるかで行う。`Bot` は `Actor` を実装する型である。確認：公開スキーマ
- Comment の本文は `bodyText` から求め、改行と記号の処理は表示側の規則（DESIGN.md の「行の種類と状態」）に従う

**自分へのメンション**。コメント、レビューの本文、レビューコメント、PR の本文の `bodyHTML` に、自分への `user-mention` のリンク（`class` に `user-mention` を含み、`href` が自分のユーザーページを指す `a` 要素。ログイン名は大文字と小文字を区別しない）があり、投稿者が自分でなければ `mentioned` にする。投稿者、本文、URL はそのコメント、レビュー、または PR の本文から求め、そのコメントは `comment` と `reply` にしない。MENTIONED_EVENT は使用しない。確認：所有者の確認（2026-11-05、bufferings-hello/hello-merge-queue#10）。会話のコメント（10:50:15）には MENTIONED_EVENT が 3 秒遅れて（10:50:18）生じた。インラインのレビューコメント（11:40:04）では、通知の reason は `mention` だったが、6 分待っても MENTIONED_EVENT は生じなかった。どちらの `bodyHTML` も `class="user-mention notranslate"` と `href="https://github.com/bufferings"` のリンクだった。Quote reply で引用した返信（11:48:01）の `bodyHTML` では、引用の中のメンションが `class` のない普通のリンクになった。

**チームへのメンション**。通知を合図にタイムラインを取得し、コメント、レビューの本文、レビューコメント、PR の本文の `bodyHTML` に、自分が属するチームへの `team-mention` のリンクがあれば `mentioned` にする。投稿者と本文はそのコメントから求め、そのコメントは `comment` にしない。本文の文字列から `@org/team` を検索する方法は使用しない。確認：所有者の確認（2026-11-04）。別のアカウントが公開 PR で `@bufferings-hello/shiibar-check` をメンションすると、MENTIONED_EVENT は生じず、通知の reason は `team_mention` だった。`involves:@me` と `team:` の検索には 5 分待っても現れなかった。`bodyHTML` では `class="team-mention"` のリンクになり、`data-id` がチームの databaseId と一致した。通知の `latest_comment_url` は PR の最新のコメントを指し、通知の原因のコメントを示さない。HTML の形は API の仕様ではない（DESIGN.md の未決）。

**Reply**。次のレビュースレッド（コードの行に付くスレッド）の id を記録し、id でスレッドのコメントを取得する。記録したスレッドの自分以外のコメントを、1 コメントにつき 1 行の `reply` にする。対象はどの PR のスレッドでもよい。`comment` にも該当するコメント（自分の PR の、自分がコメントしたスレッドへの返信）は `reply` だけにする（Mentioned を Comment より優先する規則と同じ考え方）。`mentioned` と `reply` の両方に該当するコメントは `mentioned` だけにする。Bot の投稿は、自分のスレッドへの返信でも自分へのメンションでも、常に `bot_comment` にする（Bot comments の設定に従い、Needs action にしない）。

- 自分がコメントしたスレッド
- 自分がメンションされたスレッド。メンションより後のコメントだけを対象にする

`PullRequestReviewThread` は `createdAt` を持たないので、`timelineItems(since:)` でスレッドを絞り込まない。新しいコメントはコメントの `createdAt` で判定する。確認：公開スキーマ。

**行の本文と飛び先**。

- `MentionedEvent`、`ReviewRequestedEvent`、`AddedToMergeQueueEvent`、`RemovedFromMergeQueueEvent` は `url` を持たない。`IssueComment`、`MergedEvent`、`ClosedEvent` は `url` を持つ。確認：公開スキーマ
- Review requested とマージキューの行は PR の URL を開く
- Review requested の本文は、自分宛てが `for you`、チーム宛てが `for <slug> team`（チームの `slug`）である
- Merged と Closed の `actor` は出来事の `actor.login` で、本文は `null` である
- Removed from merge queue の `actor` は出来事の `actor.login`（チェックの失敗では `github-merge-queue`、手動では操作した人）である。本文は理由とキューに追加した人で、`Checks failed · added by alice` の形にする。理由は `reason` の `failed_checks` を `Checks failed`、`manual` を `Removed manually` とし、それ以外の値はそのまま使用する
- キューに追加した人は、出来事の `enqueuer` から求めない。bufferings-hello/hello-merge-queue#9 では、所有者が追加したのに `enqueuer` が `github-merge-queue[bot]` だった。取り除きごとに、同じ PR の ADDED_TO_MERGE_QUEUE_EVENT のうち、まだ対応させていない最も古いものと対応させ、その `actor.login` を使用する。必要なら、その PR の ADDED_TO_MERGE_QUEUE_EVENT を `since` の範囲に関係なく取得する
- 確認：2026-11-05 に gh の GraphQL で bufferings-hello/hello-merge-queue を確認した。#9 は `reason` が `merged`、`actor` が `github-merge-queue` で、同じ時刻に MergedEvent があった。#5 は `reason` が `failed_checks`、`actor` が `github-merge-queue`、#10 は `reason` が `manual`、`actor` が所有者だった。公開スキーマでは、`RemovedFromMergeQueueEvent.reason` は `String` で、`PullRequest.mergeQueueEntry` は base ブランチのマージキューの 1 件のエントリである。1 つの PR が同時に 2 回キューに追加されるか、取り除きが追加の順と異なる順に起きるかは確認していない（DESIGN.md の未決）

**チームへのメンションの対象**。チームへのメンションの判定は、通知に限らず、どの契機で取得したタイムラインにも適用する。

**チーム宛てのレビュー依頼**。チームの所属は、owner のスコープではスコープのトークン（Members: Read）、Public では通知用の classic PAT（`read:org`）で取得する。Public の fine-grained PAT では `reviewRequests` と REVIEW_REQUESTED_EVENT の `requestedReviewer` が `null` になるので、`null` の PR だけ通知用の classic PAT で依頼を読み直す。確認：所有者の確認（2026-11-04）

- `notifications` と `read:org` の classic PAT では、`requestedReviewer` が Team（`slug`、`combinedSlug`、`databaseId`）で返った
- 「Public repositories」の fine-grained PAT では、どちらの `requestedReviewer` も `null` で、エラーはなかった
- `Members: Read` の fine-grained PAT と、`notifications` と `read:org` の classic PAT で、GraphQL の `organization.teams(userLogins:)` が所属を返した。classic PAT では REST の `GET /user/teams` も全 organization のチームを返した。fine-grained PAT は 1 つの所有者に限られるので、Public の fine-grained PAT では所属を読めない（0 件で、エラーにならない）
- 同じレビュアーに再びレビューを依頼すると、別の id の REVIEW_REQUESTED_EVENT が生じた（DESIGN.md の「Review requested の行」の「再び依頼された場合は新しい行を生成する」のとおりに動作できる）

### 初めて検出した PR の取得

PR を初めて検出したとき、または監視中に戻ったときは、`since` を付けずに次を取得し、自分のコメント、レビュー、レビューコメント、PR の本文の id と、自分がコメントしたスレッドと自分がメンションされたスレッドを記録する。以後の取得は「出来事の取得の範囲」の `since` を使用する。

- PR の会話のコメント（`comments`）
- レビューと、各レビューのコメント（`reviews` と `PullRequestReview.comments`）
- レビュースレッドと、各スレッドのコメント（`reviewThreads` と `PullRequestReviewThread.comments`）
- 今も続くレビュー依頼は `reviewRequests`（現在の状態）から求め、依頼した人と時刻は、`itemTypes: [REVIEW_REQUESTED_EVENT]` で絞り、`since` を付けずに取得したタイムラインから求める。レビュアーごとに、そのレビュアーへの最新の REVIEW_REQUESTED_EVENT を対応させる

どの connection も `first: 100` で取得し、`pageInfo` で次のページを取得する。入れ子の connection（レビューとスレッドのコメント）は、親の要素ごとにページを取得する。REVIEW_REQUESTED_EVENT は `last: 100` で新しい 100 件だけを取得する。1 つの connection のページは 10 ページ（1,000 件）までとし、超えた分は取得せずに `warn` のログを出力する。各 connection が 100 件以下の PR では、この取得は 1 回の GraphQL の要求で終わる。

### 出来事の取得の範囲

- 出来事は、そのスコープで最後に取得に成功した時刻から 5 分さかのぼった時刻以降を `since` に指定して取得する。監視開始時刻より前にはしない。新しく検出した PR も同じである。行の鍵（node id）で重複を除く
- 今も続くレビュー依頼は、時刻に関係なく `review_requested` として中核へ渡す。取得の範囲が制限するのは、ほかの出来事の取得だけである。中核は、依頼が監視開始時刻以降なら通知し、監視開始時刻より前なら通知しない（DESIGN.md の「監視開始より前の出来事」）
- 取得の成功は DESIGN.md の「取得の成功と失敗」の定義に従う。そのスコープの検索と状況の取得がエラーなく終われば成功で、最後に取得に成功した時刻（Updated … ago と出来事の取得の範囲の始まり）を進める。権限不足の部分は失敗に数えない
- 出来事の取得に失敗した PR は、PR の id と、失敗した時点の取得の範囲の始まり（`since`）を取り直しの一覧に記録する。次の取得ではその `since` から取り直し、成功すれば一覧から消す。重複は行の鍵（node id）で除く
- 通知の `since` と `Last-Modified` は常に進める。通知を合図にした取得に失敗した PR も取り直しの一覧に加える。取得できるスコープに属さない PR（取得を止めたスコープ、disabled のスコープ、どのスコープにも属さない PR）の通知は従来どおり無視し、何も妨げない
- 3 回続けて出来事の取得に失敗した PR には `events_fetch_failed` を付け、`message` に `owner/repo#number` を示す。取り直しは取得のたびに続け、成功したら警告を削除する
- `since` が `createdAt` と `updatedAt` のどちらで絞り込むか、境界を含むかはスキーマに記載がない（「Filter timeline items by a `since` timestamp.」だけである）。重なりと重複の除去は、この不明点に依存しないための措置である

### Reaction

- 監視中の PR ごとに、自分の会話のコメント、レビュー、レビューコメント、自分の PR の本文の id を集める。以後の取得で新しい自分のコメントの id を追加する
- 件数は `reactionGroups` の `content`（`ReactionContent`）ごとの `reactors.totalCount` から、`viewerHasReacted` が真なら 1 を引いて求める。確認：公開スキーマの `ReactionGroup`
- `IssueComment`、`PullRequestReviewComment`、`PullRequestReview`、`PullRequest` は、いずれも `Reactable` を実装し `reactionGroups` を持つ。確認：公開スキーマ
- 基準は最初に集めたときの件数である。ただし、そのスコープの前回の取得より後に投稿されたものは 0 を基準にする（DESIGN.md の「Reaction の行」）。一度も取得に成功していないスコープでは、前回の取得の時刻の代わりに監視開始時刻（`watch_started_at`）を使用する
- 基準値は次の順で決める。まず、上の 0 を基準にする例外（そのスコープの前回の取得より後に投稿されたもの）を適用する。それ以外のコメントは、PR が監視中になった直後（初めての検出と、監視中に戻ったとき）の最初の Reaction の取得を基準値として中核へ渡し、行を生成しない（DESIGN.md の「Reaction の行」の「監視が戻った時点の件数を基準にする」。M1 の中核で `watching` が偽の PR を扱う処理と同じ）

### トークンと Keychain

- トークンは、通知用の classic PAT（`notifications` と `read:org`）が 1 つ、owner のスコープごとの fine-grained PAT が 1 つ、Public の fine-grained PAT（「Public repositories」、権限なし）が 1 つである（DESIGN.md の「トークン」）
- classic PAT は通知の取得と、Public のチームの所属とチーム宛ての依頼の読み直しにだけ使用する
- `notifications` だけの classic PAT は、GraphQL の `baseRef.compare` の `behindBy` とレビュー依頼のチームの `slug` を読めない（`INSUFFICIENT_SCOPES`）。確認：所有者の確認（2026-11-03）。Public の取得に専用の fine-grained PAT を使用するのはこのためである
- classic PAT の付与済みのスコープは、応答の `X-OAuth-Scopes` ヘッダーで分かる。`read:org` は organization とチームの所属の読み取りを許可する。確認：docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps
- fine-grained PAT は 1 つの user または organization の資源だけにアクセスでき、公開リポジトリの読み取りを常に含む。確認：docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens
- SAML SSO の組織では、classic PAT の承認が必要である。未承認で複数の組織にアクセスすると、結果からその組織の分が除かれ、`X-GitHub-SSO: partial-results; organizations=...` が返る。単一の組織への 403 では `X-GitHub-SSO` に承認の URL が含まれる。確認：docs.github.com/en/rest/authentication/authenticating-to-the-rest-api の「Personal access tokens and SAML SSO」。fine-grained PAT は発行時に承認される（同ページ）。どの応答でも `X-GitHub-SSO` が付いたら `sso_required` の警告を付ける。`partial-results` のヘッダーは organization の名前ではなく id を返すので（確認：同ページの例 `X-GitHub-SSO: partial-results; organizations=21955855,20582480` と「the ID of the organizations」の記述、2026-11-05）、警告の文面とボードは organization を名指しせず「SSO authorization required」とする。ヘッダーに承認の URL があれば `settings_status` の `sso_urls`（配列）に加え、なければ空にする（アプリは GitHub のトークンの設定ページを示す）。設定画面は SSO の承認の状態を常には表示せず、警告があるときだけ表示する。`/notifications` の応答に `X-GitHub-SSO` が付くかは確認していない（DESIGN.md の未決）
- トークンの期限は、classic PAT と fine-grained PAT のどちらも、REST と GraphQL の応答の `github-authentication-token-expiration` ヘッダー（`2026-12-03 13:03:23 UTC` の形式）で分かる。確認：所有者の確認（2026-11-03）。期限の 7 日前から `token_expiring` を付ける。ヘッダーがなければ警告しない。期限後は 401 の扱いになる（通知用のトークンは「取得の失敗と再試行」）。GitHub のドキュメントに期限前の通知の記述はない（managing-your-personal-access-tokens と token-expiration-and-revocation を確認）
- 通知用のトークンは必須である。登録されていない間はどのスコープも取得せず、すべてのスコープに `no_token` を付ける
- トークンの持ち主は `viewer.login` で求め、いつも通知用のトークンの持ち主と比べる。取得のたびに確かめ、異なればそのスコープの取得を止めて `token_owner_mismatch` を付ける。トークンを差し替えると、次の定期取得で自動で再開する
- Keychain は generic password として、service と account の組で保存する。service は `shiibar-gh`、account は通知用が `notifications`、Public が `public`、owner のスコープが `scope:<小文字の owner>` である。表示に使用する owner の表記は DB のスコープの記録から求める。`reset` で復元したスコープは、最初に取得に成功して owner のログイン名を読み直すまで、account の小文字の owner を表示する（「スコープの kind と復元」）。`public` と `notifications` という owner は `scope add` で拒否するので、account は衝突しない
- `token_set` と `token_test` の要求はログに出力しない（DESIGN.md の「ワイヤ形式」）。トークンは DB、ログ、エラーの文面、`token_test` の応答に含めない
- テストは実際の Keychain に触れない。デーモンの Keychain の操作は 1 つの trait にまとめ、`dev-ingest` ビルドだけが偽の実装に切り替えられるようにする（「テストの方法」）
- マージキューは、公開リポジトリ（マージキュー有効）で、owner のスコープの権限の fine-grained PAT が `mergeQueueEntry`、`mergeQueue`、ADDED_TO_MERGE_QUEUE_EVENT と REMOVED_FROM_MERGE_QUEUE_EVENT をエラーなく返した。確認：所有者の確認（2026-11-04）。非公開リポジトリのマージキューは GitHub Enterprise Cloud の organization だけで使用でき（github/docs の data/reusables/gated-features/merge-queue.md）、必要な権限は未決である。権限は追加せず、読めなければ `permission_missing` にする

### トークンの登録とテスト

- `token set` は保存するだけで、テスト取得をしない。保存すると、そのトークンの最後のテストの結果を消去する。未登録の owner への `token set <scope>` は `not_found`（exit 2）にする
- `token test <target>` は、標準入力が端末でなく、空でもなければ、標準入力のトークンを保存せずに検証する。それ以外は保存済みのトークンを検証する（design/ の Settings の「Test again」、DESIGN.md の「トークンの登録とテスト」）。持ち主の不一致も結果に示す。テストの手順は次の「テストの手順」に従う
- `token set public` と `token test public` は Public の fine-grained PAT、`token set notifications` と `token test notifications` は classic PAT を対象とする

**テストの手順**（所有者が了承、2026-11-05）。データの内容ではなく権限の有無だけを確かめ、項目ごとに 1 回問い合わせる。権限のエラーなら Failed と足りない権限の名前、データがなくてもエラーでなければ OK、確かめる対象がなければ確認できないことを返す。`results` の要素はこの 3 つの結果を区別できる形にする。

- owner のスコープ：その owner のリポジトリを 1 つ選ぶ（PR は不要）。PRs, reviews, comments は PR の一覧、Checks は既定のブランチの最新のコミットの GitHub Actions の workflow run（Actions: Read）と Commit status（Commit statuses: Read）の両方、Behind base は既定のブランチを自分自身と比べる compare、Team membership は org のチーム、Merge queue は既定のブランチの `mergeQueue` で確かめる。Team membership は org だけを対象とし、user のスコープでは対象外にする。リポジトリがない、またはコミットがない場合は確認できないことを返す
- Public：関わっている公開 PR のリポジトリ、なければ自分の公開リポジトリを選び、どちらもなければ確認できないことを返す。Team membership は classic PAT で確かめる
- classic PAT：Notifications、Team membership（`read:org`）、Scopes（`X-OAuth-Scopes` に `notifications` と `read:org` があるか）の 3 項目

Failed に示す足りない権限の名前は、次の表で項目から求める。REST が `x-accepted-github-permissions` ヘッダーを返したときは、その値を使用する（R5 の所有者の確認で、check-runs の 403 が `checks=read` を返した）。

| Checks | Commit statuses、Actions（足りないほうを示す） |
| Behind base | Contents |

| Merge queue | 不明（非公開リポジトリ。DESIGN.md の未決） |

- `notifications` という owner は、`public` と同じく `scope add` でエラーにする
- scope remove は Keychain のトークンも削除する。ただし、DB にそのスコープのトークンの登録の記録があるときだけ Keychain を操作する（読み取りと同じ条件）。再登録は `scope add` のあとに `token set` で行う。状態は DESIGN.md の「スコープ」のとおり戻る

### レート制限

- GraphQL の一次レート制限は、PAT を含めてユーザーごとに 1 時間 5,000 ポイントである。同じユーザーのすべてのトークンは、この 5,000 を共有する。確認：docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api の「Primary rate limit」
- GraphQL の応答は `x-ratelimit-limit`、`x-ratelimit-remaining`、`x-ratelimit-used`、`x-ratelimit-reset` を返す。`rateLimit { cost limit remaining used resetAt nodeCount }` でも取得できる。ドキュメントは可能ならヘッダーの使用を推奨している。確認：同ページと公開スキーマの `RateLimit`
- 一次レート制限を超えると GraphQL は 200 とエラーを返し、`x-ratelimit-remaining` が 0 になる。`x-ratelimit-reset` まで再試行しない。確認：同ページの「Exceeding the rate limit」
- 二次レート制限：同時 100 リクエスト、GraphQL は 1 分 2,000 ポイント（mutation を含まない要求は 1 件 1 ポイント）。超えると 200 または 403 が返る。`retry-after` があればその秒数、`x-ratelimit-remaining` が 0 なら `x-ratelimit-reset` まで、どちらもなければ 1 分以上待つ。確認：同ページの「Secondary rate limits」。shiibar-gh は、二次レート制限を cost cap の上限と同じく扱う。指定の時間（`retry-after`、`x-ratelimit-reset`、指定がなければ 1 分）だけ通知を含むすべての取得を止め、`rate_limited` の時刻を待機の終わりにし、自動で再開する
- REST の一次レート制限は、認証済みで 1 時間 5,000 リクエストである。超えると 403 または 429 が返る。確認：docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api
- GraphQL の search の結果の上限は未確認である。REST の search は 1 回の検索で 1,000 件までである（確認：docs.github.com/en/rest/search/search）

shiibar-gh の動作は次のとおりである（DESIGN.md の「レート制限」）。

- 取得の間隔は設定の値で固定し、延ばさない
- 直前 1 時間の `rateLimit.cost` の合計が GraphQL cost cap の 80% を超えたら `cost_near_cap` を付ける。cost cap は GitHub の 5,000 ポイントとは別の、shiibar-gh の自主的な上限である
- 合計が cost cap に達したとき、または GitHub の残量（REST か GraphQL）が尽きたときは、通知を含むすべての取得を止め、`rate_limited` に再開の時刻を付ける。再開の時刻は、cost cap では直前 1 時間の合計が cost cap を下回る時刻、GitHub の残量では `x-ratelimit-reset` である
- 再開後は通知の `since` で停止中の通知を取得する
- 停止中の `refresh` は取得せず、すぐに `rate_limited` と再開の時刻を返す

### 取得の失敗と再試行

DESIGN.md の「取得の成功と失敗」に従う。

- ネットワークの失敗、5xx、タイムアウトは、設定の間隔で再試行する（バックオフなし）。`fetch_failed` の時刻は次の再試行の時刻で、アプリはこれから「retrying in N min」を求める
- 401 は `token_invalid` を付け、トークンを差し替えるまでそのスコープの取得を止める
- 権限不足（403、FORBIDDEN）は `permission_missing` を付け、取得できる部分の取得を続ける。権限不足の部分は失敗に数えない
- 失敗はスコープごとに区別し、ほかのスコープの取得を止めない。例外として、通知用のトークンが 401 を返すか期限を過ぎると、すべてのスコープの取得を止め、すべてのスコープに `token_invalid` を付ける
- 通知の確認が 401、期限切れ、レート制限以外の理由（ネットワークの失敗、5xx、タイムアウトなど）で失敗すると、すべてのスコープに `fetch_failed` を付ける。取得は止めず、次の確認が成功したら警告を消す
- `refresh <scope>` は、そのスコープと、全スコープに共通の通知を取得する
- `refresh` でも、前回の通知の確認から `X-Poll-Interval` の秒数がたっていなければ、通知の確認だけを省き、ほかの取得はする。前回の確認の時刻は、通知の確認を予定した取得の時刻とする（その取得が通知の確認の前に止まった場合も含む）。前回の確認の時刻は DB に保存し、デーモンを再起動しても引き継ぐ
- `refresh` は再試行の時刻を待たずにすぐに取得する。401 で止めたスコープも 1 回だけ取得し、401 が続けば止めたままにする

### 警告とワイヤ形式

- `warnings` の要素は、種類、トークン（スコープのトークンか通知用か。`rate_limited` と `cost_near_cap` は `null`）、文面、時刻を持つオブジェクトにする（形は DESIGN.md の「ワイヤ形式」）。M1 は公開していないので、M2 で文字列から型を変更する。種類は `no_token`、`token_invalid`、`token_expiring`、`fetch_failed`、`cost_near_cap`、`rate_limited`（再開の時刻）、`sso_required`、`permission_missing`、`token_owner_mismatch`、`events_fetch_failed` である
- ポップオーバーの「Add a token in Settings」は `no_token` で表す。通知用のトークンがない間は、すべてのスコープが `no_token` を持つ
- `token_test` の `results` は、項目ごとに OK、Failed（足りない権限の名前）、確認できない、のいずれかと理由を返す（「テストの手順」）
- 設定画面の値を返す要求 `settings_status` を追加する（形は DESIGN.md の「ワイヤ形式」）。値は API の残量（REST と GraphQL）、定期取得 1 回のコスト（PR status interval ごとの定期取得 1 回で使用した GraphQL のコストの全スコープの合計。Reaction の取得を含めない）、Notifications API の間隔（GitHub が最後に指定した `X-Poll-Interval` の秒数）、トークンごとの期限、classic PAT のスコープ、テスト済みか（保存済みのトークンの最後のテストの結果と時刻）、SSO の承認の URL である
- `refresh` は、定期取得と同じ内容（検索、状況、出来事、通知、Reaction）を取得し、取得と反映が終わってから応答する。失敗は応答の `warnings` に含める。取得中に受信したら、実行中の取得の完了を待って応答する
- `token_test` の `results` の要素のフィールド名は実装者が決め、完了報告に記載する
- 警告の文面と、種類ごとにメニューバーの三角と帯のどちらで示すかは、アプリ（M3）の表示で決める。M2 のデーモンは種類と時刻を正しく付ける

### REST の版

REST の要求には `X-GitHub-Api-Version` を付ける。現在の版は `2026-03-10` と `2022-11-28` で、`2022-11-28` の終了は 2028-03-10 である。ヘッダーを省略すると `2022-11-28` になる。確認：docs.github.com/en/rest/about-the-rest-api/api-versions。M2 は `2026-03-10` を使用する。Notifications API の引数と応答の項目は、`2026-03-10` のドキュメントで確認した。

### 取得と中核の分担

M1 の分担を維持する。取得処理は kind を決定して `Ingest` を作成し、中核は行の生成、未読、通知、監視開始より前の出来事の判定を行う。中核がすべての保存を担当し、取得処理は中核の取得用の API を通して取得処理の記録を読み書きする。取得処理は行、カード、未読を変更しない。取得の対象（監視中の PR、スコープ、監視開始時刻）は中核から読み取る。

- 監視中の PR は、カードが出ている PR と、カードが消えてから Days to keep watching after close を過ぎていない PR である
- 取得に成功したスコープは、PR も出来事もなくても `updated_at` を更新する。`Ingest` に省略可能な「取得に成功したスコープの一覧」を追加し、取得処理は常にこれを渡す。一覧がない `Ingest`（M1 の形の `dev_ingest`）では、M1 の規則（PR または出来事を含むスコープだけ更新する）を維持し、M1 のブラックボックステストをそのまま有効にする。この変更に合わせて、M1 の「M2 の取得処理がデーモンの中核へ渡す型と同じ型」の記述も更新する
- 状況の取得の対象は、search の結果、監視中の PR、読めなくなった PR である。読めなくなった PR は、再び読めるようになったことを検知するため、PR status interval ごとの `nodes(ids:)` に含め続ける（DESIGN.md の「カードが出る・消える条件と監視期間」）
- 監視中の判定で、Snooze 中の PR は「カードが出ている」とみなす（M1 の、Snooze を除いた表示の判定）

M2 で保存する値は次のとおりである。スキーマを v2 に上げて v1 から移行し、再起動後の復元をテストする。

### スコープの kind と復元

- kind は `repositoryOwner(login:)` の `__typename` で求める。`Organization` なら `org`、`User` なら `user` である。`Organization` と `User` はどちらも `RepositoryOwner` を実装する。確認：公開スキーマ
- `token set` はテストしないので、kind は取得のとき（`token test` を含む）に求めて保存する。取得するまでは `null` のままとする
- `reset` のあとは、Keychain にトークンがある owner をスコープとして復元する。復元したスコープの表示名は account の小文字の owner とし、最初に取得に成功したときに `repositoryOwner(login:){ login }` で owner のログイン名を読み直して、保存した表示名を更新する。DB を読めない間の `snapshot` のスコープも、`reset` のあとと同じく Keychain から求める（DESIGN.md の「DB を読めないとき」と「ワイヤ形式」）。M1 の「Public だけ」をこの規則に置き換える

## テストの方法

- **既定のビルドのテスト**。既定のビルドのデーモンを起動するテスト（daemon_startup.rs、default_build.rs）が、実際の Keychain とネットワークに触れないようにする。デーモンは、DB にトークンの登録の記録があるスコープについてだけ Keychain を読み取る。空の状態ディレクトリで起動するテストは Keychain を読み取らず、取得もしない。scope remove の Keychain の削除も、DB にトークンの登録の記録があるスコープだけで行う。`reset` の復元（Keychain の一覧の取得）と、DB を読めない間の `snapshot` のスコープを伴うテストは `dev-ingest` ビルドに移し、偽の Keychain を使用する。crates/shiibar-gh/tests/cli.rs の DB を読めないときの `reset` のテスト（`reset_works_from_the_command_line_when_the_database_is_unreadable`）も同じく移す。この方法で隔離できない場合は、本番のビルドに取得を止める切り替えを設ける案を所有者に確認する
- **偽の Keychain と偽の GitHub の切り替え**。`dev-ingest` ビルドのデーモンだけが、環境変数 `SHIIBAR_GH_DEV_KEYCHAIN`（状態ディレクトリの下の JSON ファイルへのパス）と `SHIIBAR_GH_DEV_GITHUB_URL`（REST と GraphQL の基点の URL。ループバックだけを許可する）を受け付ける。既定のビルドはこれらを無視する。`dev-ingest` ビルドは、`SHIIBAR_GH_DEV_KEYCHAIN` がなければ Keychain を持たず（トークンが保存されていない状態として動作し、保存と削除はエラーにする）、`SHIIBAR_GH_DEV_GITHUB_URL` がなければ取得しない。テストが環境変数を指定し忘れても、`cargo test --all-features` は実際の Keychain とネットワークに触れない。`dev-ingest` のデーモンは、起動時に使用する偽の Keychain と GitHub の URL をログに出力する。統合テストは、ループバックで待ち受ける偽の GitHub を起動し、要求の内容を記録して応答を返す
- **スケジューラーと時刻**。取得のスケジューラーは M1 の差し替え可能な時刻を使用する。`dev_clock_set` は、その時刻で期限の来た取得を同期で実行してから応答する。統合テストはこれで待機と再試行を確認し、sleep を使用しない

## CLI

M1 のコマンドに `token set notifications`、`token set <scope>`、`token test notifications`、`token test <scope>` を加える。`<scope>` は owner のログイン名または `public` である。`token set` と `token test` は標準入力の 1 行目をトークンとし、引数でトークンを受け取らない。末尾の改行を除く。`token set` は、標準入力が空なら使用法の誤り（exit 1）とする。`token test` は、標準入力が端末でなく、空でもないときだけトークンを読み取り、それ以外は保存済みのトークンを検証する。`settings status` を加える（`--json` を持つ）。`token test` は `--json` を持つ。すべて `--help` を持つ。`<pr>` のリポジトリ名も、大文字と小文字を区別せずに比較する（DESIGN.md の「CLI（AI 連携）」）。

## テスト

実装の前に、次の変換と判定を表にして、`crates/shiibar-ghd/tests/` のテーブル駆動テストにする。入力は GraphQL と REST の応答の JSON、出力は `Ingest` とする。表の作成で新しい挙動が必要になったら、オーケストレーターに報告する。

- `changes_requested_by` の `+N`
- 状況アイコンの値と状態ラベルへの変換。`reviewDecision` が `null`、`mergeable` が `UNKNOWN`、`behindBy` を取得できない場合を含む
- 失敗したチェックの名前（job、Commit status、`+N`、`dynamic` の run の除外）
- 出来事の kind の判定（Bot、自分の投稿、自分の PR、チーム宛て、Include requests to my teams）
- 自分へのメンションとチームへのメンションの判定（インラインのレビューコメント、引用の返信、自分の投稿を含む）
- Reply の対象のスレッドの記録と、メンションより後のコメントの判定
- Reaction の件数（自分の Reaction を除く）と基準値
- 監視中の PR の判定と `watching`
- `since` の決定と重複の除去
- 初めて検出した PR と監視中に戻った PR の取得（自分のコメントとスレッドの記録、レビュー依頼と REVIEW_REQUESTED_EVENT の対応、ページの上限）
- 監視中に戻った直後の Reaction の基準値（行を生成しない）
- 通知のまとめ方（スコープごとに 1 件なら個別、2 件以上ならまとめ通知。同じコメントの Reaction をまとめた通知は 1 件と数える）
- cost cap の 80% の警告、上限による停止と再開、二次レート制限の待機
- `warnings` の付与と解除

統合テストの要件は次のとおりである。

- 実際のデーモンを、偽の GitHub と偽の Keychain で起動する。順序の同期は `subscribe` で取り、sleep を使用しない
- `token set` から `list` までの一連の操作で、M1 の `dev_ingest` と同じ行、通知、未読が生じることを確認する
- 304 と `X-Poll-Interval`、`If-Modified-Since` の受け渡し、二次レート制限の 403 と `retry-after`、一次レート制限の `x-ratelimit-remaining: 0` を偽の GitHub で再現し、デーモンが待機することを確認する。待機の確認には `dev_clock_set` を使用する
- `token_set` と `token_test` の要求とトークンが、ログ、DB、エラーの文面、`token_test` の応答に現れないことを確認する
- 取得の失敗の間、前回の内容が残り、`warnings` に `fetch_failed` が付くことを確認する。401 でそのスコープの取得が止まり、ほかのスコープの取得が続くことを確認する
- 取得に成功したスコープの `updated_at` が、PR も出来事もない場合も更新されることを確認する。一部の PR の出来事の取得が失敗しても、スコープの最後に取得に成功した時刻と通知の `since` が進み、失敗した PR の出来事が次の取得で記録した `since` から取得されることを確認する。続けて失敗した PR に `events_fetch_failed` が付き、成功で削除されることを確認する
- 通知用のトークンがない間はどのスコープも取得せず `no_token` が付くこと、通知用のトークンの 401 で全スコープの取得が止まること、持ち主の不一致でそのスコープが止まり、トークンを差し替えると次の定期取得で再開することを確認する
- 二次レート制限で全スコープの取得が止まり、指定の時間のあとに自動で再開することを確認する
- `refresh` が取得と反映の完了後に応答し、上限による停止中はすぐに `rate_limited` を返すことを確認する
- 前回の通知の確認から `X-Poll-Interval` の秒数がたつ前の `refresh` は `/notifications` を呼び出さずにほかの取得をし、たったあとの `refresh` は呼び出すことを確認する
- `/notifications` の 502 ですべてのスコープに `fetch_failed` が付き、次の確認の成功で外れることを確認する
- `reset` のあとに偽の Keychain のトークンからスコープが復元されることを確認する。scope remove で偽の Keychain のトークンが削除されることを確認する
- 手動の Unsnooze で、Snooze より前の未配信の通知の記録が消えることを確認する
- スキーマの v1 から v2 への移行と、再起動後の復元を確認する
- `SHIIBAR_GH_DEV_KEYCHAIN` と `SHIIBAR_GH_DEV_GITHUB_URL` を読み取るコードが `cfg(feature = "dev-ingest")` の内側にあることを、レビューで確認する。`dev-ingest` のデーモンが起動時に使用する偽の Keychain と GitHub の URL をログに出力することを確認する
- `dev-ingest` ビルドで環境変数を指定しないと、Keychain を持たず、取得もしないことを確認する
- テストは実際の Keychain、ネットワーク、ホームに触れない。偽の GitHub はループバックだけで待ち受ける
