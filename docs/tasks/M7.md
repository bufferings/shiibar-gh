## 実装の要点

DESIGN.md の規則をここでは繰り返さない。各項目は、どこに何を作成するかだけを示す。

### 操作の速さ

所有者の言葉：カードの操作が重い。カードが多い（50 枚程度）とスクロールが難しい。DESIGN.md「実装方針」の「操作の速さ」の 5 つの基準を満たすこと。0.4 のコードの参照で見つけた次の疑いは、どれも推定である。実装者は推定で修正せず、計測で原因を確かめてから修正し、修正の前と後の計測の値を完了報告に記載する。

1. `app/Sources/ShiibarGhApp/SelectableText.swift`：文字ごとに AppKit の `NSTextView` を 1 つ作成する。文字の選択の廃止で無くなるが、それで改善したことを計測で確かめる
2. `app/Sources/ShiibarGhApp/CardViews.swift` の `ListArea`：`ScrollView` の中の `VStack` が遅延の生成をしないので、すべてのカードを一度に生成して配置する
3. すべての `CardView` と `RowView` が `SurfaceListModel` 全体を `@ObservedObject` で監視するので、選択の変更ですべてのカードを再描画する
4. `Avatar`（`CardViews.swift`）が `body` の中で毎回 `NSImage(data:)` で画像を復号する
5. カードごとの `onGeometryChange` の状態と `ViewThatFits`（`CardViews.swift`）
6. `TimelineView(.periodic(by: 30))` が `now` をすべてのカードに渡すこと
7. `dragging` と `dropTarget` が、すべてのカードが監視するモデルの `@Published` であること
8. 見出しと行ごとに 1 つ作成する `RightClickArea` の NSView
9. カードごとの多数の `.help` 修飾子
10. 行の `more` のための、本文の省略の検出（0.5 で加える処理。計測の対象に含める）

計測の方法：

- ビルド：最適化したビルド（リリースの構成）で signpost を有効にして計る。再描画の範囲のカウンターも、このビルドで計測のフラグを有効にしたときだけ動作させる（通常の起動では動作させない）
- 計測のモード：環境変数または起動の引数で選択する計測のモードをアプリに加える。このモードは、(1) 起動時にそのアカウントの常時表示ウインドウを開き、(2) 一覧の端から端までを一定の速さでプログラムからスクロールし、(3) 各操作（選択、チェック、Dismiss、移動、タブの切り替え）を 10 回ずつ行い、(4) フレームの処理時間と、入力からフレームまでの時間を signpost で記録して要約を出力し、(5) ログイン項目の登録と通知の許可の要求を行わず、(6) 一時の UserDefaults のスイート（`UserDefaults(suiteName:)`）と一時の状態ディレクトリ（`SHIIBAR_GH_STATE_DIR`）を使用する。計測するシナリオは、スクロール、各操作、ドラッグ中の自動スクロールを伴うホバーである
- 試験用のデータ：Dismiss していない 200 枚のカード（各カードに行 3 件。メンションの 3 行の本文、Mute の対象のカード、`+ N more PRs` を含む）を、既存の `dev-ingest` ビルドのデーモン（`DevIngest`）で読み込む手順を作成する。手順はリポジトリの中のスクリプトまたはテストの補助として残し、誰でも同じデータで再現できるようにする。アバターはローカルの `file://` の画像にする（または、アバターなしで計り、画像の復号は別に計る）。データの手順はトークンを一切渡さない（トークンを渡すと、デーモンが実際の Keychain に保存するため）。実際の状態ディレクトリ、Keychain、GitHub には触れない
- 条件：すべての `+ N more PRs` を展開した状態で、All（Group by が `Repository`、Then by が `None`）と Review のそれぞれで計る。0.5 では `Show muted` をオンにして、0.4 と同じ枚数のカードを表示する
- スクロール：一覧の端から端まで一定の速さでスクロールする通過で、メインスレッドの処理時間の最大値と、16 ms を超えたフレームの数を記録する。使用する Instruments のテンプレートと指標の名前は Apple のドキュメントで確かめ、記憶で決めない
- 操作：クリック（選択）、チェック、Dismiss、移動（ドラッグ＆ドロップ、`Move to …`、D／T／W、⌥↑／⌥↓）、タブの切り替えで、入力のイベントからその結果を描画したフレームまでの時間を signpost で計る。各操作を 10 回行い、最大値を記録する
- 慣らし：1 回の慣らしの通過のあとの値で判定する。最初の通過（冷えた状態）の値も記録して表に載せるが、判定には使用しない
- 再描画の範囲：選択とチェックの変更で再描画したビューを、上のカウンターで数え、変化したカードと、キーのヒント、操作の帯、表示する値が変化したビュー（タブの未読の数、`+ N more PRs` の点）だけであることを確かめる
- 修正の前（0.4.0 のコード）と後の両方を同じ手順で計り、表にして完了報告に記載する。0.4.0 のコードには計測のモードがないので、0.4.0 のコードを同じ条件で計る方法（計測のモードだけを加えた作業用のブランチなど）は実装者が決め、完了報告に記載する

合格の基準は DESIGN.md「実装方針」の「操作の速さ」と「定数」の計測の条件のとおりである（慣らしのあとで、スクロールと自動スクロールの 16 ms を超えるフレームが 0、各操作が 100 ms 以下）。計測の値が基準を満たしても、所有者の実機で重いと判断されたら、段階 6 を待たずに作業を止めて報告する。

### 文字の選択の廃止とクリック、ダブルクリック、ドラッグ

- 削除：`SelectableText.swift` とその使用、文字の選択の状態（選択の有無の読み取り、解除）、右クリックのメニューの `Copy`、⌘C の文字の選択による分岐、`MainMenu.swift` の Copy の文字の選択への追従（Edit の Copy は DESIGN.md「通常のアプリへの切り替え」のとおり、検索欄では文字、一覧ではリンク）
- 追加：ダブルクリックで開く操作（1 回目のクリックで選択を待たせないこと、一連のクリックの 1 回目が同じカードの見出しまたは行の、コントロールでない部分だったときだけ開くこと、コントロールは一連のクリックにつき 1 回だけ動作すること）、鎖のアイコンとチェックの形の 1 秒の表示。クリックの判定（押した対象とクリックの回数から、選択、開く、コントロールの操作、何もしない、を決める分類）は ShiibarGhCore に分離して `swift test` で確かめる
- 変更：カードと行の開くアイコンを削除する（開く操作はダブルクリック、⏎、`Open on GitHub`）。× をカードの 3 行目の右端から 1 行目の右端（鎖のアイコンの右）に移動し、鎖のアイコンとの間隔をほかのアイコンどうしより広くする。3 行目は時刻で終わる。カードが狭いときに 3 行目の時刻を 4 行目に折り返す規則は変更しない
- ドラッグ：つまみ ⋮⋮ を削除し、Review と Mine ではカードのコントロールの上を除くどこからでもドラッグを開始する（DESIGN.md「押したときの動作」。段階 1 で、ボタンの上からのドラッグを試作で検証する案をやめ、この規則に固定した）。ドラッグとクリック、ダブルクリック、チェックボックス、右クリック、キーの監視（`Surfaces.swift` の `keyMonitor`）が競合しないことを試作で確かめる（下の「危険な箇所」）
- ドロップの位置から `place` の引数への変換（`app/Sources/ShiibarGhCore/CardDrop.swift`）と ⌥↑／⌥↓ の位置：DESIGN.md「押したときの動作」の「隠したカードと位置」の 1 つの規則で求める。隠したカードは `Show muted` がオフの間の Mute の対象と検索に一致しないカードだけで、`+ N more PRs` にまとめたカードと折りたたんだ区画のカードは基準のカードである。0.4 の Mute の対象のカードの規則は削除する
- 自動スクロール：ドラッグ中の上端と下端の帯（「定数」）で、端に近いほど速くスクロールする。使用した API と確認の方法を完了報告に記載する。配置先の macOS（14）の SwiftUI でスクロールの位置を滑らかに変更する方法がなければ、下の NSScrollView を使用する

### 複数のカードの操作

- チェックの状態はアプリだけが持ち、ワイヤとデーモンには加えない。ポップオーバーとウインドウで別々に持つ。状態と規則（範囲、解除の条件、帯の操作の対象にできるカードの判定、複数のカードの要求の順）は ShiibarGhCore に分離して `swift test` で確かめる
- 要求はカードごとの既存の `place` と `dismiss` で送る。同じ位置にまとめて配置するカードが移動の前の表示の順を保つように、アプリが要求の順と位置（`at`、`before`）を決める。たとえば先頭へのまとめての配置は、最後のカードから順に `at: top` で送るか、1 枚目を `at: top` にして残りを順に直後へ配置する。どちらにするかは実装者が決め、完了報告に記載する
- `Done` へのまとめての移動で移動の前の表示の順を保つのは、`Done` の時刻が操作の時刻になる移動（`Move to Done`、`Done` へのドラッグ）だけである。`Add to Review`／`Add to Mine` で閉じた配置なしの PR を `Done` に配置するときは、0.4 と同じく検知の時刻の順になる
- ドロップの基準のカードがまとめて移動するカードの 1 枚なら、同じ方向で最も近い、移動しないカードを基準にする。並びが変化しない移動は要求を送らない
- ⇧ クリックの起点は、チェックをすべて解除したときと、起点のカードを表示しなくなったときに消す。起点がなければ押したカードだけをチェックする
- デーモン：`Done` に移動した時刻が同じカードは、あとから移動したカードを先に並べる（DESIGN.md「Review」）。同じ取得で検知した自動の移動で時刻が同じカードは、0.4 と同じく PR の鍵の順である。今の `done_at` は秒の単位なので、同じ秒の移動の順を保存する値が必要かを段階 5（DB）で決め、必要なら版 7 に加える
- 帯の操作の失敗は、失敗したカードだけを元に戻してチェックを残し、帯を 1 回の操作につき 1 つ表示する

### Mute

- デーモン：判定（`crates/shiibar-ghd/src/engine.rs` の Mute の判定）を DESIGN.md「Mute」の判定に変更する。自分が作成した PR のカードへのリポジトリと利用者の Mute の不適用（自分が作成した PR の中でも、Mute している利用者の行は Mute の対象の行のまま）、PR 単体の設定の 3 つの値、Unmute の PR の中の利用者の Mute の行（普通の行になる）、My team mentioned を通すこと（青い未読、通知、通知を渡す時点の確認）
- 削除：区画の末尾に移動する規則とそれに伴う規則（`placement.position` を Mute の対象を末尾にした順で求めること、自動の追加を Mute の対象でないカードの末尾にすること、`place` の `before` に Mute の対象を指定したときの `invalid`、`at` と位置の既定を Mute の対象のカードの間で解釈すること）
- ワイヤ：カードに `pr_mute` を加え、`muted` の理由を新しい判定に合わせる。`mute` と `unmute` の `pr` を DESIGN.md「ワイヤ形式」のとおりにする（`unmute` は、なしにしてもリポジトリまたは作者の Mute の対象なら Unmute にする）
- アプリ：`Show muted` の切り替えと青い点（アカウント全体で判定し、表示中のタブに関係しない）、Mute の対象のカードを表示しないこと（見出しの数、`+ N more PRs`、空の区画、グループの有無、選択の順、⇧R の範囲、ドロップの位置）、タブの未読の数に表示していないカードのメンションを数えること、通知を押したときに `Show muted` をオンにすること、`Unmute this pull request` のメニュー、手元の Mute の反映（「操作の反映」）。All の並びと Review、Mine の順から Mute の対象を末尾にする処理を削除する（`Listing.swift`）
- Unmute の設定は PR の記録とともに削除する（カードの削除、owner とアカウントの削除）
- `unmute pr`（ワイヤ、CLI、設定画面の `−`）は、PR の記録がない名前では一覧から名前を除くだけで `ok` を返す。`not_found` の条件は DESIGN.md「ワイヤ形式」の `unmute` のとおり
- チェックの解除：Mute の操作（メニュー、設定画面、CLI）で `Show muted` がオフの間に Mute の対象になったカード、`Show muted` をオフにしたとき、disabled にした owner、読めなくなった PR のチェックを解除する（DESIGN.md「複数のカードの操作」）

### チームへのメンションの検索

- `GET /user/teams` の結果から organization の `login` を保存する（今の `TeamRec` は `database_id` と `slug` だけ）。この取得はアカウントごとに 1 回で、0.4 と同じ要求である。ページ送り（`per_page` は最大 100。docs.github.com で確認）が今の実装で処理されているかも確かめる
- organization の owner で、その owner の My team mentioned の List がオンなら、その organization の自分のチームごとに 2 つの検索（開いている PR と閉じた PR）を `Search` の要求に加える（`convert::search_queries`、`Run::owner_inner` の `query Search`）。`OR` で複数のチームをまとめられないことはオーケストレーターが確認した（下の「確認した外部仕様」）。検索の数が owner ごとに異なるので、`Search` の変数の数とログの `variables: N` も owner ごとに異なる
- チームの検索だけで発見した PR は、知らない閉じた PR と同じく、取得の範囲の中で復帰の契機の行を生成したときだけ取り込む（DESIGN.md「API の使い分け」の検索で発見した PR の扱い）。開いている PR のレビュー依頼の例外は適用しない
- `Search` の中のチームの検索の 1 つ（別名 1 つ）だけが GraphQL のエラーを返し、ほかが応答したときは、owner の失敗にせず、そのチームの検索だけをその回は省き、失敗した要求のログと同じ形で記録して、次の取得で再び検索する（DESIGN.md「取得の成功と失敗」）
- organization の owner で所属するチームが 5 を超える場合は、実装者は計測した `Search` のポイントの消費（`rateLimit.cost`）をオーケストレーターに報告してから先に進む。報告せずに検索の数に上限を設けない
- `team:` の確認（下の「確認した外部仕様」）はオーケストレーターが行った。この作業は確認の記録を前提にしてよく、オーケストレーターを待たない

### Dismiss からの復帰の契機

- `engine.rs` の復帰の契機の判定、Dismiss している間に生成する行、新しく発見した閉じた PR で生成する行、記録だけが残る PR の再発見、クローズのあとの自動の Dismiss の例外、n 日を数える契機、閉じた PR の Review の `Done` への配置を、DESIGN.md「Dismiss」の 7 種類の行に変更する。List がオフの間に記録した行は契機にしないので、チーム宛ての依頼は List がオンのときだけ契機になり、List の規則がそのまま契機の範囲を決める。クローズのあとの自動の Dismiss の例外の「クローズのあと」は、行を生成した時点で PR がマージまたはクローズ済みと分かっていたことを指す（0.4 と同じ）

### 見出しの API の表示と設定画面

- アプリ：見出しのバーを、百分率を中に表示する 1 本のバーにし、数字とツールチップを削除する（片方の API の値が `null` なら、もう片方の値を使用する）。設定画面のアカウントの設定に API usage の見出しと 2 行（GraphQL API、REST API。どちらも 80% 以上は警告の色）を加える。値はワイヤの `rate_limit` から求める。`rate_limit` は、`graphql` と `rest` がそれぞれ `null` になりうる点でワイヤの変更である（「範囲」のワイヤ形式）
- owner の設定：`AccountsTab.swift` のセグメントを削除し、見出しで縦に並べる。右の領域は縦にスクロールできるようにする。アカウントの設定の画面も、収まらないときは同じく縦にスクロールする
- ツールチップ：0.4.0 で表示が遅い原因を調べる（SwiftUI の `.help` と AppKit の `toolTip` の違い、ポップオーバーとパネルのウインドウの種類、キーウインドウかどうかなど。どれも推定）。同じアプリの中の標準の `NSButton` の `toolTip` と待ち時間を比べて確かめる

### メニューバーのアイコン

- `Surfaces.swift`：アイコンを押したとき、そのアカウントの常時表示ウインドウが開いていれば、ポップオーバーを表示せずにウインドウを前面に表示してキーウインドウにする。フォーカスが移るので `popover_opened` を送る（ウインドウにフォーカスがある間は開いているとして扱う規則のまま）。まとめ通知を押したときも、ウインドウが開いていれば同じくウインドウを前面に表示する

### DB と移行

- スキーマは版 7。`SCHEMA_VERSION` を 7 にし、版 6 から版 7 への移行を加える。版 6 のすべての表とデータを残し、PR 単体の Unmute の列を加える（既存の PR は Unmute なし）。`Done` の同じ時刻の順を保存する値が必要かはこの段階（作業の順序の 5）で決め、必要ならその列も加え、既存のカードの今の並びを保つ値を設定する
- 版 5 と版 4 からの移行は、行き先を版 7 にする（アカウントだけを引き継ぐ規則は変更しない）
- 0.4 で保存した順位（`place_rank`）はそのまま使用する。0.4 は Mute の対象のカードを区画の末尾に表示していたが、順位は区画の中の 1 つの順で保存しているので、0.5 ではその順位の位置に表示する（`Show muted` をオンにすると、0.4 と表示の位置が異なる場合がある）。0.4 の実装が Mute の対象のカードにどう順位を付けたか（`store.rs`、`engine.rs`）を確かめ、0.5 の表示の位置が順位のとおりになることをテストで確かめる

- アプリは 0.4 の UserDefaults をそのまま読み込む。新しい項目（カードの中の `+ N more` の展開、行の本文の展開、`Show muted`）のキーを加え、既定値から始める。キーの名前は実装者が決め、完了報告に記載する

## 危険な箇所と確認すること

- **操作の速さ**：上の「操作の速さ」。推定で修正せず、計測してから修正する。遅延の生成をする一覧（`LazyVStack` など）に変更すると、ドラッグ中の自動スクロール、通知を押したときのカードへのスクロール、`+ N more PRs` の展開、選択の移動に伴うスクロール、高さの異なるカードのスクロールの位置の保持に影響する。2 の試作で、これらが従来どおり動作することを確かめる
- **クリック、ダブルクリック、ドラッグ、チェックボックスの両立**：1 回目のクリックで選択を待たせないこと（ダブルクリックの判定を待つと選択が遅れる）、ドラッグの開始のしきい値、コントロールの上ではドラッグを開始しないこと、コントロールが一連のクリックにつき 1 回だけ動作すること、⇧ クリックの範囲、右クリック、Space のキーと検索欄の入力の区別。SwiftUI と AppKit のジェスチャー、ドラッグ＆ドロップ、`NSEvent` の API の動作は記憶で決めず、Apple のドキュメントと試作で確認し、確認方法を完了報告に記載する
- **試作の進め方**：段階 2 の最初に、遅延の生成をする一覧に、200 枚のカード（試験用のデータ）、チェックボックス、1 行目の鎖のアイコンと ×、コントロールの上を除くカード全体からのドラッグ（区画の間、`Done`、自動スクロール、見出しへのドロップ）、ダブルクリック、鎖のアイコンを組み込む。試作で示すことは、上の両立と、操作の速さの基準である。オーケストレーターが開発版のインストールを所有者に依頼し（`scripts/dev-install.sh` はエージェントが実行しない）、所有者が実際のデータで確認する。所有者が使用できると判断してから本体の実装に進む
- **隠したカード（Mute の対象と検索）**：ドロップと ⌥↑／⌥↓ の位置を基準のカードの間で決め、隠したカードを「隠したカードと位置」の規則で扱うこと（1 枚目の上半分だけが先頭の隠したカードより上になる非対称を含む）、`+ N more PRs` にまとめたカードと折りたたんだ区画のカードを基準のカードとして扱うこと、`Move to …` が隠したカードを含む先頭または末尾に配置すること、`placement.position` が Mute の対象を含む順になったこと、`+ N more PRs` と見出しの数と空の区画が表示するカードで決まること
- **PR 単体の Unmute**：`unmute pr` の 3 つの場合（Mute からなし、Mute からなしでもリポジトリが Mute なので Unmute、なしで作者が Mute なので Unmute）、`not_found`、`mute pr` が Unmute を Mute に変更すること、Unmute の PR の中の利用者の Mute の行、PR の記録の削除で Unmute も消えること、自分が作成した PR（リポジトリと利用者の Mute でカードは Mute の対象にならず、Mute している利用者の行は Mute の対象の行のまま）
- **チームへのメンションの検索**：検索の数が増える。4 つの検索で 1 ポイントであることだけを確認した。organization の owner で所属するチームが 5 を超えるときは、計測したポイントの消費をオーケストレーターに報告してから進める（上の「チームへのメンションの検索」）
- **自動スクロールの API**：使用した API と確認の方法を完了報告に記載する。配置先の macOS（14）の SwiftUI でスクロールの位置を滑らかに変更する方法がなければ NSScrollView を使用する
- **テストの隔離**：テストは実際の Keychain、ネットワーク、状態ディレクトリ、ホーム、通知センター、ログイン項目、標準の UserDefaults に触れない。試験用のデータの手順も一時ディレクトリだけを使用する

## 段階 1 の結果

段階 1（指示書レビュー）は 2026-11-13 に完了した。決定はすべて DESIGN.md とこの指示書に反映済みである。

修正が必要だった項目：

1. 操作の速さの計測：最適化したビルドで signpost を有効にして計り、再描画のカウンターは同じビルドで計測のフラグのときだけ動作させる。条件は Dismiss していない 200 枚のカード（各 3 行）、すべての `+ N more PRs` を展開、All（`Repository`／`None`）と Review、0.5 は `Show muted` をオン。計測のモード（ウインドウを開く、プログラムからのスクロール、各操作 10 回、signpost と要約、ログイン項目と通知の許可を行わない、一時の UserDefaults と状態ディレクトリ）を加え、試験用のデータは `file://` のアバターでトークンを渡さない。基準は、慣らしの 1 回のあとで 16 ms を超えるフレームが 0（60 Hz）、各操作 100 ms 以下。ドラッグ中の自動スクロールを計測に加え、疑いを 5 つ追加し、再描画の範囲に値が変化したビューを含めた（「操作の速さ」）
2. 位置の基準：隠したカードは `Show muted` がオフの間の Mute の対象と検索に一致しないカードだけで、まとめたカードと折りたたんだ区画のカードは基準のカードである。ドロップと ⌥↑／⌥↓ に 1 つの規則を適用する（DESIGN.md「押したときの動作」の「隠したカードと位置」）
3. チームへのメンションの検索：チームの検索だけで発見した PR は、復帰の契機の行を生成したときだけ取り込む。チーム宛てのレビュー依頼だけの PR に `team:` が一致するかは未決だが、一致しても List がオフの規則を迂回しない。チームが 5 を超えるときは消費を報告してから進む。チームの検索の 1 つだけのエラーは owner の失敗にしない
4. `team:` の確認はオーケストレーターが所有者の `gh` CLI のログインで、読み取りの要求だけで行った（結果は下の「確認した外部仕様」）
5. `Done` へのまとめての移動で表示の順を保つのは、時刻が操作の時刻になる移動だけで、閉じた PR の `Add to …` は検知の時刻のまま
6. ダブルクリックは、一連のクリックの 1 回目が同じカードの見出しまたは行の、コントロールでない部分のときだけ開く。コントロールは一連のクリックにつき 1 回だけ動作する。ShiibarGhCore のクリックの判定としてテストする

## 確認した外部仕様

`team:` の検索の確認（2026-11-13、オーケストレーターが所有者の `gh` CLI のログインで実施。トークンのスコープは gist、read:org、repo、workflow。読み取りの GET と GraphQL の query だけで、mutation は使用していない。organization とチームの名前は記録しない）：

- GraphQL の `search(query: "is:pr team:ORG/TEAM", type: ISSUE)` は `team:` に従う。`closed` のチームで `issueCount` 2 と 2 つの PullRequest を返し、同じ検索の REST の `GET /search/issues` と同じ件数だった。2 件とも、会話のコメントにそのチームのメンションがあった（PR のコメントを参照して確認）

- 結論：「チームごとに 2 つの検索を並べ、チームの検索だけで発見した PR は復帰の契機の行でだけ取り込む」設計のまま進める。チームの検索の実装はオーケストレーターを待たない
