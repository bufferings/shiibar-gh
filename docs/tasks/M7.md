## 実装の要点

DESIGN.md の規則をここでは繰り返さない。各項目は、どこに何を作成するかだけを示す。

### 操作の速さ

所有者の言葉：カードの操作が重い。カードが多い（50 枚程度）とスクロールが難しい。DESIGN.md「実装方針」の「操作の速さ」の 4 つの基準を満たすこと。0.4 のコードの参照で見つけた次の疑いは、どれも推定である。実装者は推定で修正せず、計測で原因を確かめてから修正し、修正の前と後の計測の値を完了報告に記載する。

1. `app/Sources/ShiibarGhApp/SelectableText.swift`：文字ごとに AppKit の `NSTextView` を 1 つ作成する。文字の選択の廃止で無くなるが、それで改善したことを計測で確かめる
2. `app/Sources/ShiibarGhApp/CardViews.swift` の `ListArea`：`ScrollView` の中の `VStack` が遅延の生成をしないので、すべてのカードを一度に生成して配置する
3. すべての `CardView` と `RowView` が `SurfaceListModel` 全体を `@ObservedObject` で監視するので、選択の変更ですべてのカードを再描画する
4. `Avatar`（`CardViews.swift`）が `body` の中で毎回 `NSImage(data:)` で画像を復号する
5. カードごとの `onGeometryChange` の状態と `ViewThatFits`（`CardViews.swift`）

計測の方法：

- 試験用のデータ：1 つのタブ（All と Review の両方で確かめる）に 200 枚のカード（各カードに行 3 件。メンションの 3 行の本文、Mute の対象のカード、`+ N more PRs` を含む）を、既存の `dev-ingest` ビルドのデーモン（`DevIngest`）で読み込む手順を作成する。手順はリポジトリの中のスクリプトまたはテストの補助として残し、誰でも同じデータで再現できるようにする。実際の状態ディレクトリ、Keychain、GitHub には触れない（`SHIIBAR_GH_STATE_DIR` に一時ディレクトリを指定する）
- スクロール：デバッグビルドで、メインスレッドの 1 フレームの処理時間を計る（Instruments のテンプレート、`os_signpost`、またはフレームの時刻を記録する計測用のコード）。一覧の端から端まで一定の速さでスクロールしたときの最大値と、16 ms を超えたフレームの数を記録する。使用する Instruments のテンプレートと指標の名前は Apple のドキュメントで確かめ、記憶で決めない
- 操作：クリック（選択）、チェック、Dismiss、移動（ドラッグ＆ドロップ、`Move to …`、D／T／W、⌥↑／⌥↓）、タブの切り替えで、入力のイベントからその結果を描画したフレームまでの時間を `os_signpost` などで計る。各操作を 10 回行い、最大値を記録する
- 再描画の範囲：選択とチェックの変更で再描画したカードの数を、計測用のカウンター（デバッグビルドだけ）で数え、変化したカードだけであることを確かめる
- 修正の前（0.4.0 のコード）と後の両方を同じ手順で計り、表にして完了報告に記載する

合格の基準は DESIGN.md「実装方針」の「操作の速さ」と「定数」の計測の条件のとおりである。計測の値が基準を満たしても、所有者の実機で重いと判断されたら、段階 6 を待たずに作業を止めて報告する。

### 文字の選択の廃止とクリック、ダブルクリック、ドラッグ

- 削除：`SelectableText.swift` とその使用、文字の選択の状態（選択の有無の読み取り、解除）、右クリックのメニューの `Copy`、⌘C の文字の選択による分岐、`MainMenu.swift` の Copy の文字の選択への追従（Edit の Copy は DESIGN.md「通常のアプリへの切り替え」のとおり、検索欄では文字、一覧ではリンク）
- 追加：ダブルクリックで開く操作（1 回目のクリックで選択を待たせないこと、ボタンの上では開かないこと）、鎖のアイコンとチェックの形の 1 秒の表示
- 変更：カードと行の開くアイコンを削除する（開く操作はダブルクリック、⏎、`Open on GitHub`）。× をカードの 3 行目の右端から 1 行目の右端（鎖のアイコンの右）に移動し、鎖のアイコンとの間隔をほかのアイコンどうしより広くする。3 行目は時刻で終わる。カードが狭いときに 3 行目の時刻を 4 行目に折り返す規則は変更しない
- ドラッグ：つまみ ⋮⋮ を削除し、Review と Mine ではカード全体からドラッグを開始する。ドラッグとクリック、ダブルクリック、チェックボックス、右クリック、キーの監視（`Surfaces.swift` の `keyMonitor`）が競合しないことを試作で確かめる（下の「危険な箇所」）
- ドロップの位置から `place` の引数への変換（`app/Sources/ShiibarGhCore/CardDrop.swift`）：見出しは `at: top`、`+ N more PRs` は `at: bottom`、カードの上半分は直前、下半分は直後（次に表示しているカードの直前、なければ `at: bottom`）、表示していない Mute の対象のカードとの前後関係。0.4 の Mute の対象のカードの規則は削除する
- 自動スクロール：ドラッグ中の上端と下端の帯（「定数」）で、端に近いほど速くスクロールする

### 複数のカードの操作

- チェックの状態はアプリだけが持ち、ワイヤとデーモンには加えない。ポップオーバーとウインドウで別々に持つ。状態と規則（範囲、解除の条件、帯の操作の対象にできるカードの判定、複数のカードの要求の順）は ShiibarGhCore に分離して `swift test` で確かめる
- 要求はカードごとの既存の `place` と `dismiss` で送る。同じ位置にまとめて配置するカードが移動の前の表示の順を保つように、アプリが要求の順と位置（`at`、`before`）を決める。たとえば先頭へのまとめての配置は、最後のカードから順に `at: top` で送るか、1 枚目を `at: top` にして残りを順に直後へ配置する。どちらにするかは実装者が決め、完了報告に記載する
- デーモン：`Done` に移動した時刻が同じカードは、あとから移動したカードを先に並べる（DESIGN.md「Review」）。今の `done_at` は秒の単位なので、同じ秒の移動の順を保存する値が必要なら版 7 に加える
- 帯の操作の失敗は、失敗したカードだけを元に戻してチェックを残し、帯を 1 回の操作につき 1 つ表示する

### Mute

- デーモン：判定（`crates/shiibar-ghd/src/engine.rs` の Mute の判定）を DESIGN.md「Mute」の判定に変更する。自分が作成した PR のカードへのリポジトリと利用者の Mute の不適用（自分が作成した PR の中でも、Mute している利用者の行は Mute の対象の行のまま）、PR 単体の設定の 3 つの値、Unmute の PR の中の利用者の Mute の行（普通の行になる）、My team mentioned を通すこと（青い未読、通知、通知を渡す時点の確認）
- 削除：区画の末尾に移動する規則とそれに伴う規則（`placement.position` を Mute の対象を末尾にした順で求めること、自動の追加を Mute の対象でないカードの末尾にすること、`place` の `before` に Mute の対象を指定したときの `invalid`、`at` と位置の既定を Mute の対象のカードの間で解釈すること）
- ワイヤ：カードに `pr_mute` を加え、`muted` の理由を新しい判定に合わせる。`mute` と `unmute` の `pr` を DESIGN.md「ワイヤ形式」のとおりにする（`unmute` は、なしにしてもリポジトリまたは作者の Mute の対象なら Unmute にする）
- アプリ：`Show muted` の切り替えと青い点、Mute の対象のカードを表示しないこと（見出しの数、`+ N more PRs`、空の区画、グループの有無、選択の順、⇧R の範囲、ドロップの位置）、タブの未読の数に表示していないカードのメンションを数えること、通知を押したときに `Show muted` をオンにすること、`Unmute this pull request` のメニュー、手元の Mute の反映（「操作の反映」）。All の並びと Review、Mine の順から Mute の対象を末尾にする処理を削除する（`Listing.swift`）
- Unmute の設定は PR の記録とともに削除する（カードの削除、owner とアカウントの削除）

### チームへのメンションの検索

- `GET /user/teams` の結果から organization の `login` を保存する（今の `TeamRec` は `database_id` と `slug` だけ）。この取得はアカウントごとに 1 回で、0.4 と同じ要求である。ページ送り（`per_page` は最大 100。docs.github.com で確認）が今の実装で処理されているかも確かめる
- organization の owner で、その owner の My team mentioned の List がオンなら、その organization の自分のチームごとに 2 つの検索（開いている PR と閉じた PR）を `Search` の要求に加える（`convert::search_queries`、`Run::owner_inner` の `query Search`）。検索の数が owner ごとに異なるので、`Search` の変数の数とログの `variables: N` も owner ごとに異なる
- 実装の前に、下の「確認すること」の 3 項目を実際の応答で確かめ、結果を完了報告とオーケストレーターに報告する。GraphQL の search が `team:` に従わない場合は、実装を止めて報告する（代わりの方法は所有者が決める）

### Dismiss からの復帰の契機

## 危険な箇所と確認すること

- `Show muted` と青い点、renovate の PR が隠れること、自分の PR が Mute されないこと、`Unmute this pull request`、Mute の対象の PR へのメンションの通知を押したときの表示
- 行の本文の `more` と `less`、カードの中の `Show less` とポップオーバーを閉じても展開が残ること
- メニューバーのアイコンを押したときのウインドウ、ツールチップの表示までの時間
- 見出しの `API` のバーと百分率、設定画面の API usage、owner の設定の 1 枚の画面
- 実データ：チームだけがメンションされた PR がカードになり通知されること、Dismiss したカードがチームへのメンション、チームがメンションされたスレッドへの返信、チームへのレビューの依頼で復帰すること

## 完了条件

ローカルで次のコマンドが成功すること。CI は push 後に実行されるので、完了条件に含めない。

```sh
cargo test --workspace --all-features --locked
cargo test --workspace --locked
cargo clippy --all-targets --all-features --locked -- -D warnings
cargo deny check
swift test --package-path app
```

- 操作の速さの基準（DESIGN.md「実装方針」）を、修正の前と後の計測の表で示している
- 仕様との比較と独立検証で未解決の指摘がない
- 所有者の確認（段階 6）が終わっている

## ルール

- ソースコード、コメント、テスト名、文字列は英語で記述する。UI の文言はボードと DESIGN.md の英語の表記に従う
- 仕様を日本語のまま引用しない。英語に訳して DESIGN.md の節名を示す
- 指示書の範囲外の機能を追加しない。DESIGN.md に記載のない動作が必要になったら、実装を止めてオーケストレーターに報告する
- 外部仕様（GitHub の API、Apple の API）を記憶だけで実装しない。公式ドキュメント、公開スキーマ、実データで確認し、完了報告に確認方法を記載する
- GitHub には書き込まない。確認の要求も読み取りだけにする。所有者の organization、チーム、非公開のリポジトリの名前を、リポジトリの中のファイルと完了報告に記述しない
- 依存のパッケージ（Swift Package と crate）は、公開から 7 日以上たった版だけを使用する
- エージェントが cargo を実行するときは、所有者が使用している `target/` と競合しないよう、別の `CARGO_TARGET_DIR` を指定する
- `scripts/dev-install.sh` と `scripts/dev-uninstall.sh` はエージェントが実行しない
- コミットはオーケストレーターの指示があるまで行わない
- 完了報告には、実装者が決めた点と、仕様の矛盾や不足を記載する
