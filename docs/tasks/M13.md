# M13: アサインの行と通知（0.10）

Status: 指示書

最初に CLAUDE.md、docs/DESIGN.md、docs/DEVELOPMENT.md と、docs/design/ の Main.html と SettingsOwner.html を確認すること。挙動の正は DESIGN.md、見た目の正は docs/design/ である。M1〜M12 の指示書は完了した時点の記録で、DESIGN.md と食い違う箇所は DESIGN.md が優先する。0.10 で変更した文書は docs/DESIGN.md と docs/design/ のボード（Main.html、SettingsOwner.html）である。指示書と DESIGN.md が食い違う場合は、実装を止めてオーケストレーターに報告する。

## ゴール

アカウント自身が、自分が作成していない PR にアサインされたことを、出来事の行（種類 Assigned）と macOS の通知で知らせる。行の 1 段目にはアサインした人を表示する。自分で自分をアサインした行は既読で生成し、通知しない。Dismiss しているカードは、アサインされると復帰する。Review と Mine への配置は、これまでどおり自動では行わない。DB を版 11 に上げ、既存の owner の出来事の表に Assigned を既定値（List と Notify のオン）で加える。

## 範囲

### 含める

- 出来事の取得に ASSIGNED_EVENT を加えること（DESIGN.md「実装方針」の「API の使い分け」の表、「行の種類の判定」の表の Assigned。`fetch.rs` の `ITEM_TYPES` と `timeline_nodes`）
- 行の種類 Assigned の判定と生成（「行の種類と状態」の表、「行の種類の判定」、「行の本文と移動先」、「自分が起こした出来事の行」、「監視開始より前の出来事」の最後の 2 文）
- 復帰の契機（「Dismiss」の「復帰の契機」の表と本文、「カードの表示と監視」の知らない閉じた PR の規則）
- ワイヤ形式の種類の値 `assigned`（「ワイヤ形式」）。`dev_ingest` の `kind` にも `assigned` を加える
- 出来事の表への種類の追加と、表の見出しのグループ（Reviews and mentions の 3 番目。「行の種類と状態」の表と「表の見出し」）。CLI の `owner events` と `owner events set` は種類の値をそのまま受け付ける
- DB の版 11 と、版 10 からの移行（「状態の保存」の「0.9 からの更新」）
- アプリの行のラベル、アイコン、アバターと名前、移動先（「行の見た目」「行のラベル」「行の本文と移動先」。Main.html の `Row Assigned`）
- 設定画面の出来事の表の行（SettingsOwner.html の Events の表と Copy table のシート）
- サンドボックスのデータ（`scripts/lib/make-data.py` の `edge-cases` と `scripts/lib/screenshot_data.py`）に Assigned の行を加えること（下の「サンドボックスのデータ」）

- アサインの解除（UNASSIGNED_EVENT）の行、ほかの人のアサインの行

- 監視開始時刻より前のアサインを行にする例外（レビューの依頼にだけある例外。DESIGN.md のとおり適用しない）
- 自動の Dismiss の例外にすること（DESIGN.md の例外の一覧は変更しない）
- バージョンの変更（0.10.0 への変更はリリースの手順で行う）とリリースの公開

## 確定事項

決めた事項は DESIGN.md とボードに反映済みで、要点は次のとおりである。挙動は DESIGN.md だけに従う。

- 行を生成する条件：自分が作成していない PR の `AssignedEvent` で、`assignee` が `User`、その login がアカウントの login と一致する（大文字と小文字を区別しない）。`assignee` が null、`Bot`、`Mannequin`、`Organization` のときと、自分が作成した PR へのアサイン（誰が行っても）は行にしない
- 1 段目はアサインした人（`actor`）。`actor` が null なら名前とアバターを表示しない。本文はない。移動先は PR のページ（`AssignedEvent` は URL を持たない）
- `actor` がアカウント自身なら既読で生成し、通知しない。カードはこの場合も復帰する（Reopened と同じ）
- 復帰の契機の 8 種類目。知らない閉じた PR を取り込む契機にもなる
- 配置の規則（「Review」「Mine」、「カードの状態」の表）は変更しない
- 既定値は List と Notify のオン。通知の判定（owner の Notify、Skip draft pull requests、Mute）は、ほかの種類と同じ規則に従う
- アイコンは人の形（頭の円と肩の弧。16 × 16 の線、線の太さは他の行のアイコンと同じ）。形は Main.html の `Row Assigned` の SVG のとおり

## 実装の要点

### 実装の前に確認すること

- `AssignedEvent` の項目と型は DESIGN.md の「行の種類の判定」の表に記録してある（公開スキーマの照会と実データで確認、2026-11-23）。取得の要求を変更したら、テストの偽の GitHub（`crates/shiibar-ghd/tests/fake_github`）にも `AssignedEvent` を加える
- 0.7 で出来事の表に 3 種類を加えたときの移行（版 9 から版 10）の実装と、そのテスト（`crates/shiibar-ghd/tests/migration.rs`）を読み、同じ形で版 11 への移行を加える
- 行の種類を加えたときに変更が必要な箇所を、既存の種類（`ready_for_review`、`reopened`）の参照から洗い出す。指示書のレビューで分かった箇所は次のとおりで、これに限らない
  - proto（`crates/shiibar-gh-proto/src/lib.rs`）：`IngestKind`、`RowKind`、`EventKind` と `EventKind::ALL`（長さが変わる）。`EventKind` は `Ord` を導出しているので、列挙の位置が出来事の表の並び（ワイヤ、DB の読み込み、CLI）を決める。`TeamReviewRequested` の次に置く。種類の名前のテストも更新する
  - デーモンのモデル（`crates/shiibar-ghd/src/model.rs`）：proto とは別の `EventKind` と `RowKind`（`stored_enum!`、`both_ways!`、`EventKind::ALL`）、`From<proto::IngestKind>`、`RowKind::event()`、`is_return_trigger()`（説明の「the seven rows」も）、`is_own_action_kind()`、`label()`（通知のタイトルに使用する `Assigned`）。`has_actor()` の除外の一覧には加えない（アサインした人で Mute できるのが仕様どおりである）
  - 取得（`fetch.rs`）：`ITEM_TYPES` と `timeline_nodes()`。`Events`、その続き、新しく発見した PR の出来事の取得の 3 つが使用する。`assignee` は共用体なので `assignee { __typename ... on User { login } }` と書く。要求の文字列を照合するテスト（`fetch_comment_times.rs`、`labels_black_box.rs`）も合わせる
  - 変換（`convert.rs`）：`AssignedEvent` の分岐。`assignee` の login をアカウントの login と大文字と小文字を区別せずに比べ、`actor` を行の actor とアバターに、移動先を PR の URL にする
  - DB（`store.rs`）：版の分岐（今は版 9 以下だけを移行の対象にしている）に版 10 を加え、`migrate_v10_to_v11` を `migrate_v9_to_v10` のあとの同じ連鎖に置く。版 11 は表の定義を変えないので、`owner_events` への既定値の追加（既存の owner ごと）だけである。版 10 と書いたコメントを更新する
  - アプリ（`app/Sources/ShiibarGhCore`）：`Wire.swift` の `RowKind` と `EventKind`（`CaseIterable` の順が表の順）、`Presentation.swift` の `RowText.label`、`SettingsText.eventGroups` と `eventTitle`、`BoardIcons.swift` の新しいアイコンと `row(_:)` の分岐。`showsActor` は変更しない（既定で表示する）

### サンドボックスのデータ

- `edge-cases`：Assigned の行を、未読（ほかの人がアサイン）、既読（自分でアサイン）、`actor` のない行、Mute の対象のカード、Dismiss から復帰したカードで、それぞれ 1 つ以上含める
- `screenshots`：README の画像に写る範囲を大きく変えない。All だけの PR のどれか 1 つに、ほかの人がアサインした未読の行を 1 つ加える程度にする

## 仕様から決まる動作

次の動作は、既存の規則からそのまま決まる。実装者は別の動作を作らない。

- 同じ出来事を再び取得しても、行は出来事の id で 1 つである。アサインを解除してから再びアサインすると、新しい `AssignedEvent` なので新しい行になり、Dismiss しているカードは再び復帰する
- `actor` が null の行は、自分の操作として扱わない（未読で、表に従って通知する）
- Bot によるアサインは、人によるアサインと同じく扱う。止めるにはその Bot を Mute する
- Draft の PR の Assigned の行は、ほかの種類と同じく `Skip draft pull requests` に従う（Ready for review の例外を適用しない）
- 復帰の契機が Assigned の行で、PR が閉じている場合は、レビューの依頼と Reopened と同じく n 日を数え、自動の Dismiss の対象にする
- Mute の対象のカードも Assigned の行で復帰する。行は灰色で、通知しない

## テストの方法

- M2.md〜M12.md の「テストの方法」のとおり、実際の Keychain とネットワークに触れない。`swift test` は、実際のデーモンを使用するテスト（`SHIIBAR_GH_TEST_DAEMON`）を省略せずに実行する
- 新しく確かめること（デーモン）：
  - 判定：自分へのアサインで行を生成すること（大文字と小文字の違う login を含む）、ほかの人へのアサイン、`assignee` が null と `Bot` のアサイン、UNASSIGNED_EVENT、自分が作成した PR へのアサイン（ほかの人、Bot、自分のどれが行っても）で行を生成しないこと
  - 自分で自分をアサインした行が既読で、通知されないこと。ほかの人のアサインが未読で、表の Notify、owner の Notify、Skip draft pull requests、Mute に従って通知されること
  - 復帰：Dismiss しているカードがアサインで復帰すること（自分でアサインした場合を含む）。List がオフの間のアサインでは復帰しないこと。知らない閉じた PR がアサインの行で取り込まれること
  - 監視開始時刻より前のアサインを行にしないこと（今もアサインされていても）
  - 配置：アサインの行を生成しても、配置なしのカードが配置なしのままであること
  - 出来事の表：新しい owner の表に Assigned が既定値で入ること、表の並び、`owner_events_set` と `owner_events_copy`
  - 移行：`tests/data/` に版 10 のスキーマを `schema_v09.sql` としてタグ v0.9.1 から固定し（既存のファイルは、取り出したタグのアプリの版で名付けている）、既定値でない出来事の表を持つ owner、PR、既読と未読の行、配置、`Done`、Dismiss と Dismiss の記録、Mute、ラベルを入れた版 10 の DB を作る。移行のあと、Assigned が既定値で加わり、ほかの値がすべて同じであること。移行に失敗したらロールバックして版 10 のまま読めない状態になること（既存の `a_failed_move_…` のテストと同じ形）。移行した DB を保存して開き直せること。0.9 の状態ディレクトリでデーモンが起動すること。版 9 以前の DB からも版 11 まで移行すること
  - 既存のテストの更新：`migration.rs` の `assert_eq!(SCHEMA_VERSION, 10)` と `*_moves_to_version_10_*` のテスト、版がプログラムより新しい DB をエラーにするテスト（`user_version = 10` で作っている。`SCHEMA_VERSION + 1` に変える。10 のままにすると移行の対象になって失敗する）
  - 閉じた PR が Assigned の行で復帰したとき、n 日後に自動で Dismiss されること。Mute の対象のカードが Assigned の行で復帰し、行が灰色で通知されないこと
  - 偽の GitHub の `Events` の応答に `AssignedEvent` を含めたブラックボックスのテスト
- 新しく確かめること（アプリ）：Assigned の行のラベル、アイコン、アバターと名前を表示すること、移動先が PR のページであること、設定画面の表の並び（Review requested to my team の次）
- 既存のテストで種類の数や並びを前提にしているもの（出来事の表の行数、復帰の契機の数など）は、削除せず新しい値に書き換え、書き換えたテストを完了報告に記載する

## 危険な箇所と確認すること

- DB の移行は、利用者のデータを書き換える唯一の処理である。版 10 の DB を移行したあとで、出来事の表のほかの種類の値、PR、行、配置が変わらないことをテストで確かめる
- 行の種類の値はワイヤ形式に現れるので、古いアプリが知らない種類を受け取ったときの扱い（`Lenient` の既存の規則）に従うことを確かめる
