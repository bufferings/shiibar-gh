# M3: Swift アプリ、署名、リリース

Status: 実装

最初に CLAUDE.md、docs/DESIGN.md、docs/DEVELOPMENT.md、docs/tasks/M1.md、docs/tasks/M2.md と、docs/design/ のすべてのボードを確認すること。挙動の正は DESIGN.md、見た目の正は docs/design/ である。指示書と DESIGN.md が食い違う場合は、実装を止めてオーケストレーターに報告する。

## ゴール

利用者がアプリをインストールすると、メニューバー、ポップオーバー、常時表示のウインドウ、設定画面、macOS の通知が、DESIGN.md とボードのとおりに動作する。アプリはデーモンを起動、停止、更新し、CLI と同じソケットでデーモンと通信する。リリース版を Developer ID で署名して公証し、GitHub Releases と Homebrew の cask で配布する仕組みをそろえる。

## 範囲

### 含める

- `app/` の Swift package（SwiftUI。足りない部分は AppKit）と、アプリのバンドルの組み立て
- デーモンのライフサイクル（「デーモンのライフサイクル」）
- ソケットのクライアント。`subscribe`（`client` は `app`）、再接続、要求と応答
- メニューバー：スコープごとのアイコン、バッジ、青い点、三角（docs/design/MenuBarIcon.html）。スコープのアイコンが 1 つもないときの shiibar-gh のアイコン
- ポップオーバー：見出し、⌄ のメニュー、帯、タブ、チップ、カード、行、キーのヒント、空の状態、DB を読めないときの表示（docs/design/Main.html、MainSnoozed.html、PublicScope.html）
- 常時表示のウインドウ（Open in window。NSPanel）
- 未読の消え方のための `seen`、`popover_opened`、`popover_closed` の送信
- キーボードの操作（DESIGN.md の「キーボード」と「選択とキー」）
- macOS の通知：個別の通知とまとめ通知、押したときの動作
- 設定画面：General、Scopes、Notifications、Watching の 4 タブ（docs/design/Settings.html）。スコープの追加と削除、背景色、トークンの登録、Create token、トークンの状態、テストの結果、API の使用量、SSO の警告
- Launch at login（SMAppService）
- デーモンと CLI の変更（「デーモンと CLI の変更」）
- 開発版のインストール：`scripts/dev-install.sh`、`scripts/dev-uninstall.sh`、ローカルの固定の署名の ID の作成
- リリース：GitHub Actions のリリースのワークフロー（Developer ID の署名、hardened runtime、公証、staple、zip、GitHub Releases）、Homebrew の cask のテンプレートと、tap を更新するワークフロー
- CI に Swift のテストのジョブと、cask のテンプレートの `brew style --cask` を追加する

### 含めない

- 「デーモンと CLI の変更」に記載のないデーモンの挙動の変更。ワイヤ形式に足りない情報がさらに見つかった場合は、実装を止めてオーケストレーターに報告する
- 実際のリリースの公開、tap への push、GitHub の Secrets の登録。所有者が行う
- GitHub への書き込み

### デーモンのライフサイクル

- `.app` の `Contents/Helpers/` に `shiibar-ghd` と `shiibar-gh` を同梱する。cask は `Contents/Helpers/shiibar-gh` へのリンクを作成する
- アプリの起動時に `info` で既存のデーモンを確認する。応答があり、`version` がアプリの版と同じなら接続する。異なれば `shutdown` で止めてから同梱のデーモンを起動する。応答がなければ同梱のデーモンを起動する
- アプリを終了するとき（⌄ のメニューの Quit と ⌘Q）は、`shutdown` でデーモンを止める。DESIGN.md の「監視開始より前の出来事」の「アプリの停止中に起きた出来事」は、デーモンがアプリと一緒に止まる前提である。shiibar-cc の DESIGN.md §8.8 と同じ方針である
- デーモンが予期せず終了した場合の扱い（再起動の有無と間隔）と、デーモンの stderr のログの扱いは、実装者が決めて完了報告に記載する。launchd は使用しない（DESIGN.md の「構成」）
- 再接続は 1 秒から倍々、上限 30 秒である（DESIGN.md の「定数」）。再接続したら、開いているスコープの `popover_opened` を再送する（DESIGN.md の「ワイヤ形式」）
- 状態ディレクトリは `SHIIBAR_GH_STATE_DIR` に従う（DESIGN.md の「定数」）。アプリはこの環境変数を起動したデーモンに引き継ぐ

### 版の番号

- Cargo.toml の `[workspace.package] version` を唯一の元にする。リリースのワークフローは、タグ `vX.Y.Z` と一致しなければ失敗する（shiibar-cc の `scripts/release/check-version.sh` に相当）
- アプリの `CFBundleShortVersionString` はこの版にする。リリース版の `CFBundleVersion` は版に固定し、開発版は `scripts/dev-install.sh` が時刻を設定する（shiibar-cc の DEVELOPMENT.md の「アイコンが反映されないとき」）
- デーモンの `info` の `version` は `CARGO_PKG_VERSION` である。開発版とリリース版は同じ版を持つので、`scripts/dev-install.sh` は shiibar-cc と同じく、アプリとデーモンを止めてから入れ替える
- cask の uninstall で残ったデーモンを止めるときは、デーモンが `--foreground` を付けて起動される点に合わせて pkill の比較のパターンを決める（shiibar-cc の `pkill -xf` は引数のない起動が前提である）

### デーモンと CLI の変更

所有者の決定（Public の追加と削除、背景色、アバター、Bot の Comment の表記）に必要な変更だけを行う。ワイヤ形式の変更は DESIGN.md の「ワイヤ形式」と M1.md の「応答の項目」にも反映する。M1.md と M2.md は完了した時点の記録で、M3 の変更が優先する。M1.md の「エラー」の `public` の `scope add` と `scope remove` を `invalid` にする例、M2.md の「トークンの登録とテスト」の `public` を `scope add` で拒否する記述は、M3 で置き換える。これらを確かめている既存のテストは、M3 の動作に合わせて変更する

- **Public の追加と削除**。`scope add public` と `scope_add` の `public` で Public を追加し、`scope remove public` で削除する。DB を空の状態で起動したとき、Public を作成しない。既存の DB の Public は残す。Public がない間、未登録の owner の公開リポジトリの PR は表示せず、取得もしない（DESIGN.md の「スコープ」）。`notifications` は引き続き `scope add` で拒否する。`reset` のあとの復元は M2 のとおり Keychain のトークンから行い、Public のトークンがあれば Public を復元する
- **背景色**。スコープに背景色を保存し、`scope` の応答に `color` を加える。値は 6 色の名前（実装者が決め、完了報告に記載する）。色は DESIGN.md の「概要とスコープ」に従い、ボードの 3 色を含め、Public の初期値をベージュにする。追加した直後は、6 色を追加の順に巡回して割り当てる。`scope_color`（`scope`、`color`）と CLI の `scope color <scope> <color>` を追加する。不正な値は `invalid` にする
- **アバター**。`card` に `author_avatar_url`（GraphQL の `author.avatarUrl`。`author` が `null` なら `null`）を加える。`avatarUrl` は `Actor` のフィールドで、「A URL pointing to the actor's public avatar.」である（公開スキーマで確認、2026-11-05）。取得するときの `size` の引数は実装者が決める
- **Bot の Comment の通知のタイトル**。`example-org · Bot comment` を `example-org · Comment` にする（DESIGN.md の「macOS 通知」）。行の種類の値（`bot_comment`）は変更しない
- スキーマを上げる場合は、M2 と同じく移行と再起動後の復元をテストする

### ソケットのクライアント

M1 の「shiibar-cc の実装から引き継ぐ注意点」のうちクライアントの項目に従う。1 行が複数回の読み取りに分かれても処理する。未知の `event`、フィールド、enum の値を無視する。

### メニューバーとポップオーバー

- MenuBarExtra で足りるかを確かめ、スコープごとのアイコン（数が増減する）、バッジ、キーボードの操作が足りなければ AppKit（NSStatusItem と NSPopover）にする（DESIGN.md の「UI」）。MenuBarExtra が複数のアイコンを動的に表示できることはドキュメントに記載がないので、最初から NSStatusItem にしてもよい。どちらにしたかと理由を完了報告に記載する
- アイコンの形は owner の種類で決まる。`kind` が `null`（取得の前）の間は user のアイコンを表示する
- チップの選択、常時表示のウインドウの位置と大きさは UserDefaults に保存する（DESIGN.md の「状態の保存」）
- 行が画面に表示されたら `seen` を送る。スクロールの外の行と、絞り込みで隠れた行は送らない
- `popover_opened` と `popover_closed` は、スコープごとに、ポップオーバーと常時表示のウインドウ（フォーカスがある間）のどちらかが開いている間を「開いている」として送る。開いている面が 0 から 1 になったら `popover_opened`、1 から 0 になったら `popover_closed` を送る
- 押したときに開く URL は、カードの見出しが `card.url`、状況アイコンが `card.links`、行が `row.url` である。`open` の要求は CLI のためのもので、アプリが使用するかは実装者が決める
- 帯の「Settings」に該当する操作は、設定画面の Scopes タブを開く
- 「retrying in N min」の N は分に切り上げ、最小を 1 とする。`events_fetch_failed` の `message`（`owner/repo#n`）は `owner/repo #n` の表記にする
- アバターの画像はアプリが `author_avatar_url` から読み込み、キャッシュする。読み込めない間は空の丸を表示する
- DB を読めない間は、ポップオーバーと設定画面に「Couldn't read saved state」と Reset を表示する

### 通知

- UNUserNotificationCenter を使用する。`notify` の `notification` の `title`、`subtitle`、`body` をそのまま表示する。受け取ったらすぐ表示する
- 個別の通知を押すと `url` をブラウザで開く。ポップオーバーは経由せず、青い点の状態は変更しない。通知にボタンは付けない
- まとめ通知を押すと、そのスコープのポップオーバーを開く
- 通知の許可を求めるタイミングは実装者が決める。行を Done にしても、通知センターの通知は消さない

### 設定画面

- 値の読み書きは `config_get` と `config_set`、表示する値は `settings_status`、スコープは `scope_*`、トークンは `token_set` と `token_test` で行う。`settings_status` は push されないので、設定画面を開いている間と `scope_changed` を受け取ったときに取り直す
- 不正な値はデーモンが `invalid` で拒否する。アプリはその値を保存せず、エラーを表示する
- アプリはトークンを保持しない。Save で `token_set` に渡したら破棄する。ログ、UserDefaults、クラッシュの記録に含めない
- スコープの追加、トークンの入力、Remove の確認、背景色の選択はボードにない。Settings.html の既存のコンポーネント（`.group`、`.item`、`.sub`、`.btn`、テストの結果のグリッド）で構成する。途中でやめた場合、追加したスコープは残し、その行に `No token` と貼り付ける欄を表示する
- Launch at login の表示は SMAppService の `status` に合わせ、`config` の値をそれに追従させる。`register()` は利用者の承認が必要な場合がある（Apple のドキュメントで確認すること）

### Keychain

アプリは Keychain に触れない。トークンの保存と読み取りはデーモンだけが行う（CLAUDE.md）。

## テストの方法

- アプリのロジック（スナップショットからの表示の状態、絞り込み、選択とキー、`seen` を送る行の決定、`popover_opened` と `popover_closed` の送り方、警告の帯と三角、トークンの状態の表記、デーモンのライフサイクルの判定）は、UI から分離して `swift test` で確認する
- ソケットのクライアントのテストは、テスト用の一時ディレクトリで待ち受ける偽のデーモン、または `SHIIBAR_GH_STATE_DIR` を一時ディレクトリにした実際のデーモン（`dev-ingest` ビルド）を使用する。デーモンの実行ファイルの場所は環境変数で渡し、絶対パスを記述しない。CI は `swift test` の前に `cargo build --features dev-ingest` を実行する
- 通知、Launch at login、ブラウザで開く処理、画像の読み込みは差し替えられる形にし、テストでは偽の実装を使用する。UserDefaults はテストで注入した suite を使用する
- テストは実際の状態ディレクトリ、ホーム、Keychain、ネットワーク、通知センター、ログイン項目、標準の UserDefaults に触れない
- `scripts/dev-install.sh` と `scripts/dev-uninstall.sh` は、`~/Applications`、ログイン項目、Keychain（署名の ID）を変更するので、エージェントは実行しない。shellcheck などの静的な確認だけを行う
- `brew style --cask` はローカルで実行しない。Homebrew の gem とキャッシュに書き込むためである。CI だけで実行する
- リリースのワークフローは Secrets がないと実行できない。エージェントは構文を確認する方法を決め、完了報告に記載する
- `swift-tools-version` は、CI のランナー（macos-15）の Xcode で使える版にする。ランナーの版は GitHub のドキュメントで確認する

## 所有者の確認（段階 6）

次の項目は、エージェントも段階 4 の検証も確かめられない。所有者が `scripts/dev-install.sh` でインストールし、実機で確認する。実装者は、確認の手順を完了報告に記載する。

- メニューバーの複数のアイコン、バッジ、青い点、三角。スコープがないときのアイコン
- ポップオーバーと常時表示のウインドウの表示、キーボードの操作、フォーカスと未読の点
- macOS の通知の表示と、押したときの動作
- 設定画面のスコープの追加、Create token のページ（`metadata=read` などの引数が受け付けられるか）、トークンの登録とテスト、Remove、背景色
- Launch at login
- 再ビルドとインストールで Keychain の許可のダイアログが出ないこと。hardened runtime の署名のデーモンが Keychain のトークンを読めること
- 所有者が Secrets を登録してリリースのワークフローを実行し、cask でインストールできること

## ルール

- ソースコード、コメント、テスト名、文字列は英語で記述する。UI の文言はボードと DESIGN.md の英語の表記に従う
- 仕様を日本語のまま引用しない。英語に訳して DESIGN.md の節名を示す
- 指示書の範囲外の機能を追加しない
- 外部仕様（Apple の API、codesign、notarytool、Homebrew の cask の DSL、GitHub Actions）を記憶だけで実装しない。公式ドキュメントまたは実物で確認し、完了報告に確認方法を記載する
- GitHub Actions の `uses:` はフルコミット SHA で固定する
- 依存のパッケージ（Swift Package と crate）は、公開から 7 日以上たった版だけを使用する（DEVELOPMENT.md の「依存クレートのクールダウン」）。追加する場合はオーケストレーターに報告する
- エージェントが cargo を実行するときは、所有者が使用している `target/` と競合しないよう、別の `CARGO_TARGET_DIR` を指定する
- 完了報告には、実装者が決めた点と、仕様の矛盾や不足を記載する
