## ゴール

利用者が複数の GitHub アカウントを登録すると、アカウントごとにメニューバーのアイコンとポップオーバーを持ち、ポップオーバーの中は owner ごとのセクションになる。トークンはアカウントごとに classic PAT 1 つ。Todo（0.1 の Needs action）は owner ごとの出来事の表と Exclusions で決まり、T キーで手でも追加できる。設定画面は General／Accounts／Watching の 3 タブになる。0.1 のデータは引き継がない。

### 識別子

- アカウントの `id` は GitHub のユーザーの数値の id（`viewer { databaseId }`。REST の `GET /user` の `id` と同じ値）を 10 進の文字列にしたもので、ワイヤでも DB でも Keychain でもこの値で識別する。node id は識別子に使用しない（DESIGN.md「トークン」）。`login` は表示と CLI の引数に使用し、取得のたびに `viewer { login }` と比較して追従する
- owner の `id` はデーモンが割り当てる識別子で、アカウントをまたいで一意にする。アプリと CLI は識別子としてだけ扱い、ログイン名として解釈しない。表示には `name` を使用する。`github_id` は `GET /users/{owner}` の数値の `id` で、SSO の警告の owner の特定に使用する。Public は `github_id` を持たない
- PR の鍵は GraphQL の node id とアカウントの `id` の組。行の鍵は出来事の node id とアカウントの `id` の組にし、合成する鍵（状態変化、Reaction）も同じくアカウントを含める
- CLI の `<account>` は login、`<owner>` はログイン名または `public` で、どちらも大文字と小文字を区別せずに解決する

### DB と Keychain

- スキーマは 0.1 と互換にせず、新しい版の番号を付ける。0.1 のスキーマ（版が古い）の DB を開いたときは「DB を読めないとき」の状態にし、`reset` で退避して空の状態で始める（M1.md の「DB を読めないとき」の「スキーマ版が古い場合は移行する」は M4 で置き換える）。版がプログラムより新しい DB は M1 のままエラーで終了する
- DB のスキーマは実装者が決め、完了報告に記載する。少なくとも、アカウント（id、login、color、登録順、トークンの記録、通知 API の since と Last-Modified、チーム、レート制限、停止の時刻）、owner（アカウント、名前、種類、`github_id`、登録順、enabled、notify、skip_drafts、監視開始時刻、最後に取得に成功した時刻）、出来事の表と Exclusions、PR（アカウント、owner、assignees）、行（アカウント、`todo_auto`、手の `todo`、`notify`）を持つ。List の実効値（`listed`）は列に保存せず、今の表と Exclusions から求めてよい
- Keychain の項目は 0.1 と別の名前（service と account の組）にし、0.1 の項目は読み込まず、削除もしない。項目の名前と内容（アカウントの配列。`id`、`login`、トークン）の形は実装者が決めて完了報告に記載する。`token reset` はこの項目を削除する
- `Keychain` の trait のエラーは、OS のエラー（`keychain_unavailable`）、項目なし、内容を解析できない（`tokens_unreadable`）を区別する。利用者が許可のダイアログで拒否したときのエラーコードは確認して記載する（「確認した外部仕様」）
- Keychain の読み取りは起動直後の最初の取得で 1 回だけ行い、DB にアカウントがあるとき、または `reset` の直後だけ読み込む（既定のビルドのテストが空の状態ディレクトリで起動しても実際の Keychain に触れないため）。`refresh` と `token reset` のあとに再読み込みする。読み込めない間に `account_add`、`account_remove`、`token_set`、`token_test`（保存済みのトークンの検証）、`public` 以外の `owner_add` を受けたら `keychain_unavailable` で拒否する。標準入力のトークンの `token_test` と `owner_add` の `public` は受け付ける
- DB を読めない間の `accounts` は空の配列である。`reset` のあとの最初の取得で Keychain を読み込み、アカウントを `id` と `login` で復元する。owner は復元しない

### 取得

- アカウントごとに 1 つのトークンで、通知（`GET /notifications`）、owner ごとの 4 つの検索、状況と出来事（GraphQL）、失敗したチェックの名前（REST）、Reaction、チームの所属（`GET /user/teams`）、assignees を取得する。M2.md の「取得の構成」のうち、通知用のトークンとスコープのトークンの使い分け、Public のチーム宛てのレビュー依頼の読み直し（DESIGN 0.1 の 198 行）は不要になる
- チームの所属は、アカウントごとに `GET /user/teams` で全チームの `id` と `slug` を取得する。owner ごとの `organization.teams(userLogins:)` は使用しない。チーム宛てのレビュー依頼とチームへのメンションの判定は M2.md の「出来事の kind」のとおりで、行の種類を `team_review_requested` と `team_mentioned` に区別する
- Approved の行は `PULL_REQUEST_REVIEW` の state が `APPROVED` で author が自分でないレビューから生成する。本文があれば `comment` の行も生成する（Changes requested と同じ）
- `reply` と `reply_mentioned` は、M2 の Reply の判定を「自分がコメントしたスレッド」と「自分がメンションされたスレッド（メンションより後）」に区別したものである。両方に該当する場合は `reply` にする
- Exclusions の利用者は、出来事の actor のログイン名と比較する。Reaction の行と状態変化の行は対象にしない。Bot の actor のログイン名は GraphQL の `Bot.login` の表記（`[bot]` の接尾辞なし）で比較する。REST の `login` に `[bot]` が付く場合だけ、Bot 型の actor に限って接尾辞を除く（DESIGN.md「Exclusions」）
- レート制限はアカウントごとに GraphQL の `rateLimit` と REST の `x-ratelimit-*` を記録し、残りが 20% を下回ったら `graphql_near_limit`／`rest_near_limit`、尽きたら `rate_limited` にする。cost cap と `cost_per_poll` の計算は削除する
- Updated … ago（アカウントの `updated_at`）は、そのアカウントの取得が終わるたびに更新する。owner ごとの最後に取得に成功した時刻は、出来事の取得の範囲のために内部で保持する
- `X-GitHub-SSO` の `organizations=` の数値の id を、そのアカウントの owner の `github_id` と比較する。一致した owner を警告の `owner` に設定し、文面を `SSO authorization required for <owner>` にする

### 行と Todo

- 行は生成時に、その owner の表の List／Todo／Notify と、Exclusions（リポジトリと利用者）と、`Skip draft pull requests` を参照して、`todo_auto` と `notify` を決めて保存する（List は保存せず、表示時に今の表から求める）。`todo` の手の値は別の列に保存し、`todo` の実効値は手の値があればそれ、なければ `todo_auto` である
- List の切り替えは表示の絞り込みで、既存の行にも即時に適用する。Exclusions の Hidden も同じく表示の絞り込みである。List only への変更と一覧からの削除で表示に戻った行のうち、Hidden の間に記録した行は、既読、`todo_auto` 偽として扱う。Hidden にする前からあった行は元の状態で表示する。Review requested の行は今の依頼の状態から求める（DESIGN.md「Exclusions」）
- Review requested と Review requested to my team の「今もやることか」は、M2 の「今も続くレビュー依頼」の判定を、チーム宛てについて「その owner のチームの行の Todo がオン」の条件を加えたものである。検索の `user-review-requested:@me` への切り替えは、チームの行の List で決める
- Todo の PR の数は「未完了の Todo の行を含む、Snooze していない PR」の数である。状況アイコンの赤で PR を Todo にする 0.1 の規則は削除する
- `done` は Todo の行だけ、`todo` は Done でない行だけを変更する（「行の状態遷移」）

### 通知

- 個別の通知のタイトルは `<account login> · <種類>`、サブタイトルは `owner/repo #番号` と PR のタイトル。まとめ通知は owner ごとにまとめ、タイトルにアカウント名、サブタイトルに owner 名を設定する（「macOS 通知」）
- owner の `notify` と `skip_drafts` の既定値はどちらもオン。通知の要否は行の `notify` と、渡す時点の owner の Notify、enabled、PR を読めるかで決める。種類ごとの設定（`notify_*`）と `bot_comments` は削除する

### ワイヤ形式と CLI

- DESIGN.md の「ワイヤ形式」の表と値の形に従う。M1.md の「応答の項目」と M2.md の「警告とワイヤ形式」は M4 で置き換える。0.1 の `scope_*`、`settings_status`、`undone`、`token_set` の `target` は削除する
- `subscribe` の `snapshot` は `accounts`、`keychain`、`db_unreadable` を持つ。`account_changed` はアカウントの値全体を送る。`account_removed` と `keychain_changed` を追加する
- `refresh` の応答の `warnings` の要素は `account` を持つ。`keychain_unavailable` と `tokens_unreadable` は `account` が `null` で、`snapshot` と `account_changed` ではすべてのアカウントの `warnings` に含める
- CLI は DESIGN.md の表のとおり。`--account` を必須とする命令で省略したら使用法の誤り（終了コード 1）。`account add` と `token set` のトークンは標準入力からだけ読み込む。`--json` の形は実装者が決め、`--help` に記載する
- `dev-ingest` ビルドに、GitHub なしでアカウントと owner を作成する要求 `dev_account_add`（id、login、トークンの有無）と `dev_owner_add`（account、owner、kind、`github_id`）を追加する。ブラックボックスのテスト、CLI のテスト、アプリの実際のデーモンを使用するテストはこれで準備する
- `dev_ingest` は、アカウントと owner を指定する形に変更し、assignees、新しい種類（`approved`、`team_review_requested`、`team_mentioned`、`reply_mentioned`）、Exclusions の判定に使用する actor、取得に成功した owner の一覧を渡せるようにする。形は実装者が決め、段階 4 の検証者が使用するので完了報告に記載する
- 偽の Keychain（`SHIIBAR_GH_DEV_KEYCHAIN`）の JSON は新しい項目の形にする。指定したパスが読めない（ディレクトリ、権限なし）ときは `keychain_unavailable`、内容が不正な JSON のときは `tokens_unreadable` にし、テストで両方を再現できるようにする
- `events`、`token_test` の `results`、`notification` の値の形（DESIGN.md が項目を挙げているもの）は実装者が決め、完了報告に記載する

### アプリ

- メニューバーはアカウントごとに NSStatusItem を 1 つ。絵柄はボード MenuBarIcon.html の仮の絵柄を全アカウント共通で使用し（owner の種類ごとの 0.1 の絵柄は使用しない）、`color` に応じてシステムカラーで塗る。右上の青い点、右下の数字、三角の配置はボード MenuBarIcon.html に従い、大きさは実装者が決めて所有者が実機で確認する
- ポップオーバーの構成はボード Main.html と Activity.html。セクションの折りたたみ、絞り込みの選択、Activity の owner のボタンの選択、常時表示のウインドウの位置はアカウントごとに UserDefaults に保存する。`+ N more PRs` の展開は保存しない
- API の使用量の 1 行は、アカウントの `rate_limit` から描く。`null` のときは `– / –` と空のバー
- キーのヒントは選択に合わせて切り替える（「キーボード」）。選択の移動にセクションの見出しと `+ N more PRs` を含める（「選択とキー」）
- 帯の文面とボタンは「警告の表示」の表。`Settings…` は設定画面をそのアカウントを選んだ状態で開く。`Retry…` と `Reset tokens…` は Keychain のダイアログを表示する。`Authorize…` は警告の `url`（なければ GitHub のトークンの設定ページ）を開く
- Keychain のダイアログは、`snapshot` または `keychain_changed` で `keychain` が `ok` 以外になったときに 1 回表示する（「Keychain を読めないとき」）。`Retry` は `refresh`、`Reset tokens` は `token_reset` を送る
- 設定画面はボード Settings.html、SettingsOwner.html、Sheets.html、Keychain.html に従う。値の読み書きはデーモンへの要求で行い、CLI を起動しない。アプリはトークンを保持せず、`account_add`、`token_set`、`token_test` に渡したら破棄する。ログ、UserDefaults、クラッシュの記録に含めない
- Add account… と Edit… のシートの Test は `token_test`（Add account… では `account` なし）、Save は `account_add` または `token_set`。Save のあと、デーモンが保存済みのトークンを検証する間、Token の行に `Checking…` を表示する
- Add owner… の Add は `owner_add`（デーモンが `owner lookup` を実行する）。`not_found` と `unreachable` をシートの欄の下に表示する
- まとめ通知を押すとそのアカウントのポップオーバーを開く。個別の通知を押すと `url` を開く
- 設定の `appearance`、`launch_at_login` の扱いは M3 のまま

## 確認した外部仕様

実装前に次を確認し、確認方法を完了報告に記載する。確認できないものは DESIGN.md の「未決」に残す。

- `viewer { databaseId login }` の `databaseId` が `Int` で非推奨でないこと（公開スキーマ）。`repo`、`notifications`、`read:org` だけの classic PAT で `databaseId` を読めること（`read:user` なし。実機で確認する）
- `GET /users/{owner}` が organization のログイン名でも `type: "Organization"` を返すこと（0.1 は GraphQL の `repositoryOwner` で判定していた）。SSO を承認していない organization での状態コード
- `GET /user/teams` の応答の `id` と `slug`、ページング（`per_page`、`Link`）、`read:org` がないときの状態コード（docs.github.com の REST の Teams）
- `X-GitHub-SSO` が GraphQL の応答にも付くか（M2 は REST のドキュメントで確認した）
- macOS の Keychain で、利用者が許可のダイアログで拒否したときのエラーコードと、再読み込みで再びダイアログが出るか（Apple のドキュメントと実機）
- NSStatusItem の画像にシステムカラーを付ける方法と、ダークのメニューバーと押下時の見え方（Apple のドキュメントと実機）
- `GET /users/{owner}` の `id`（数値）と `X-GitHub-SSO` の `organizations=` の値が同じ id であること（M2.md の「確認した外部仕様」の SSO の項目と、docs.github.com の REST の Users）
- 応答ヘッダー `x-oauth-scopes` に `repo`、`notifications`、`read:org` がどう現れるか（0.1 の `tokentest.rs` が使用済み。`repo` の下位のスコープの表記に注意する）
- `PullRequestReview` の `state` の値（`APPROVED`）と `url`（公開スキーマ）
- `assignees` のフィールド（公開スキーマ）
- Bot の actor の `login` の表記（公開スキーマの `Bot` と、実データ）

## テストの方法

- M2.md の「テストの方法」のとおり、既定のビルドのテストは実際の Keychain とネットワークに触れない。`dev-ingest` ビルドだけが偽の Keychain（JSON ファイル）と偽の GitHub（ループバックの URL）を使用する
- 偽の GitHub（`tests/fake_github`）に、`viewer { databaseId login }`（トークンごとの id と login）、`GET /user/teams`、`GET /users/{owner}`、トークンごとの `x-oauth-scopes` と `github-authentication-token-expiration` のヘッダー、assignees、`APPROVED` のレビュー、特定のアカウントや owner の応答だけに付ける `X-GitHub-SSO` のヘッダー、トークンごとに異なる検索結果（同じ owner を 2 つのアカウントに登録したときの独立を検証するため）を追加する
- 0.1 のスキーマの DB を開いたときのテストには、タグ `v0.1.0` の `store.rs` のスキーマから作成した固定の SQL を `tests/data` に保存する
- 表形式のテスト（`tests/table_*.rs`）は、アカウントと owner の形に修正する。0.1 の動作を確かめているテストは M4 の動作に合わせて変更し、削除した機能（スコープの色、cost cap、Bot comments、Include requests to my teams、Show snoozed）のテストは削除する
- 新しく確かめること：同じ owner を 2 つのアカウントに登録したときの行と通知の独立、表の変更が既存の行に影響しないこと、List の切り替えの即時反映、Exclusions の Hidden と List only、手の Todo と表の Todo の関係、Approved の行、Reply の 2 分割、チーム宛ての行の Todo の判定、持ち主の確認（同じ id、違う id、接続できない）、`already added`、Keychain を読めないときの 2 種類の警告と拒否する操作、`token reset`、0.1 のスキーマの DB を開いたときの動作、`reset` 後の Keychain からの復元、アカウントごとのレート制限と警告、SSO の owner の特定、通知のタイトルとまとめ、CLI の `--account` の必須と省略、終了コード
- アプリのロジック（セクションと折りたたみ、`+ N more PRs`、Snoozed セクション、絞り込み、選択とキーのヒント、帯とボタン、Keychain のダイアログの判定、トークンの状態の表記、使用量のバーの値）は UI から分離して `swift test` で確認する
- テストは実際の状態ディレクトリ、ホーム、Keychain、ネットワーク、通知センター、ログイン項目、標準の UserDefaults に触れない

## ルール

- ソースコード、コメント、テスト名、文字列は英語で記述する。UI の文言はボードと DESIGN.md の英語の表記に従う
- 仕様を日本語のまま引用しない。英語に訳して DESIGN.md の節名を示す
- 指示書の範囲外の機能を追加しない。DESIGN.md に記載のない動作が必要になったら、実装を止めてオーケストレーターに報告する
- 外部仕様（GitHub の API、Apple の API）を記憶だけで実装しない。公式ドキュメント、公開スキーマ、実データで確認し、完了報告に確認方法を記載する
- 依存のパッケージ（Swift Package と crate）は、公開から 7 日以上たった版だけを使用する
- エージェントが cargo を実行するときは、所有者が使用している `target/` と競合しないよう、別の `CARGO_TARGET_DIR` を指定する
- `scripts/dev-install.sh` と `scripts/dev-uninstall.sh` はエージェントが実行しない
- 完了報告には、実装者が決めた点と、仕様の矛盾や不足を記載する
