# M11: コメントの時刻、Draft の行、検索中の空の区画、Dismissed のカード、GitHub のラベル、Inbox、自分のレビュー（0.8）

Status: 段階 6（所有者の確認）まで完了。0.8.0 として公開する

最初に CLAUDE.md、docs/DESIGN.md、docs/DEVELOPMENT.md、docs/tasks/M10.md と、docs/design/ のすべてのボードを確認すること。挙動の正は DESIGN.md、見た目の正は docs/design/ である。M1〜M10 の指示書は完了した時点の記録で、DESIGN.md と食い違う箇所は DESIGN.md が優先する。0.8 で変更した文書は docs/DESIGN.md と docs/design/ のボード（Main.html、Settings.html、SettingsOwner.html）である。指示書と DESIGN.md が食い違う場合は、実装を止めてオーケストレーターに報告する。

## ゴール

0.7.0 の課題に 1 つの版で対応する。レビューコメントの時刻を公開された時刻（`publishedAt`）にし、レビューの提出より前に作成したコメントの Reaction の行と、取得の範囲より前に作成されたほかの人のレビューコメントの行が生成されない不具合を修正する。PR の Draft の解除と Draft への変更を、`Ready for review` と `Converted to draft` の行にする。Review と Mine で、検索中も空の区画を表示する。Dismissed の一覧のカードにブランチと作者を表示する。カードの見出しの最後の行に PR の GitHub のラベルを表示し、設定 `Show labels` を加える。Review と Mine の区画 `Todo` の名前を `Inbox` にし、移動のキーを T から I にする。カードの 1 行目の `Review requested` の文字の印を、レビュー待ち、承認、変更の要求の 3 つの状態を持つ自分のレビューの印にし、自分の判定のあるレビューを既読の `My review` の行にする。

デーモン、CLI、ワイヤ形式、DB（版 10 への移行）、アプリを変更する。Keychain の項目は変更しない。

## 実装の要点

### 実装の前に確認すること

外部の動作に依存する点である。DESIGN.md と異なる結果になった場合は、実装を止めてオーケストレーターに報告する。

次の点は、指示書のレビューで確認済みである（`gh api graphql` の読み取りの要求、2026-11-18。DESIGN.md に記録した）。実装の前に改めて確認する必要はない。

- Draft への変更と Draft の解除は、PR の `updatedAt` とタイムラインの更新時刻を出来事の `createdAt` まで進める（DESIGN.md「Ready for review と Converted to draft の行」）
- 2 つの出来事の `url` は `https://github.com/<owner>/<repo>/pull/<n>#event-<id>` の形で、`actor` は null を取りうる（`Actor`）。`id`、`createdAt`、`url` は null を取らない
- `publishedAt` の値：スレッドのコメントはレビューの `submittedAt` と等しく、会話のコメントは `createdAt` と等しく、レビュー自身の `publishedAt` は下書きの時刻である（DESIGN.md「コメントの時刻」）
- `PullRequest.labels` の `orderBy`（`LabelOrder`。`NAME` で名前の順）
- `labels(first: 20, orderBy: {field: NAME, direction: ASC})` を加えた `Status` の要求の `rateLimit.cost` は、50 件で 3（ラベルなしの 2 から 3 になり、`orderBy` を加えても 3）
- Draft の解除の直後の応答で、出来事と進んだタイムラインの更新時刻があるのに `isDraft` がまだ真のことがある（約 1 分で偽になる）。そのため `Skip draft pull requests` は種類で判定する

自分のレビューの項目（`reviews(author: …, states: [APPROVED, CHANGES_REQUESTED, DISMISSED], last: 1) { nodes { state } }`）についても、次の点を確認済みである（公開リポジトリに対する GraphQL の読み取りの要求、2026-11-19。DESIGN.md「API の使い分け」）。

- cli/cli の 50 件の PR に対する `Status` と同じ形の要求の `rateLimit.cost` は、この項目の有無に関係なく 3。応答の時間は、項目なしで 6.8〜7.7 秒、項目ありで 5.7〜9.0 秒
- login は変数で渡せ、`author` は大文字と小文字を区別しない。存在しない login では `nodes` が空になる
- `last: 1` は、対象の state のうち最も新しく提出したレビューを返した（microsoft/vscode#347228、#349178、#349181、rust-lang/rust#165321）

未確認の点は、1 人のレビュアーの判定のレビューが提出の順と異なる順で作成された場合の順だけである（該当する実データが見つからなかった）。その場合も、アプリは `last: 1` が返したレビューの state を表示する。

これら以外に外部の動作に依存する点が新しく見つかった場合も、確認の方法と日付を完了報告に記載する。

自分の保留中のレビューのコメントが `reviewThreads` に含まれるかは、GitHub への書き込みが必要なので確認しない（DESIGN.md「未決」）。偽の GitHub で、含まれる場合（`publishedAt` が `null`、`state` が `PENDING`）を作成して、集めないことをテストする。

### コメントの時刻

- `fetch.rs` の `COMMENT` の断片に `publishedAt` を加える。`COMMENT` を使用するすべての要求（`Events` の `IssueComment` と `reviewThreads`、`ThreadsPage`、新しく発見した PR の `Collect` とその続きの取得）が対象である。`timeline_nodes` の `PullRequestReview` は `submittedAt` のまま
- `convert.rs` の `Post::from` で、時刻を DESIGN.md「コメントの時刻」の表のとおりにする：スレッドのコメントと会話のコメントは `publishedAt`（会話のコメントで null なら `createdAt`）、レビューの本文は `submittedAt`（null なら `createdAt`。レビューの `publishedAt` は下書きの時刻なので使用しない）、PR の本文は `createdAt`
- 時刻が等しいときの位置の判定は、起点のコメントが同じ取得で得たスレッドのコメント（出来事の取得では `comments(last: 100)`）の中にあるときだけ行う。起点のコメントがその外にあるときは「後」として扱わない（DESIGN.md「コメントの時刻」）。この場合のテストを加える
- `publishedAt` が `null` のスレッドのコメントを除く処理は、`convert::events`（`posts` への追加）と `convert::collect`（自分のコメントの `own()` とスレッドの `note_thread()` を呼ぶ独自のループ）の両方に入れる。`collect` で除かないと、保留中のコメントの自分のコメントの記録とスレッドの記録が作成される
- この変更で、行の時刻（`occurred_at`）、`since` との比較、`note_thread` の `mine_at` と `mention_at`、`OwnComment.created_at`（Reaction の `comment_created_at` と `baseline_done`）がすべて公開の時刻になることを確かめる
- スレッドの前後の比較（`events` の `after`：`post.at > from`）は、時刻が等しいときにスレッドの中の位置で決める（DESIGN.md「コメントの時刻」）。1 つのレビューのコメントは同じ `publishedAt` を持つので、時刻だけの比較では同じレビューの中の続きのコメントが「後」にならない。`ThreadRec` の時刻に位置を加えるか、同じスレッドの中の順で判定するかは実装者が決め、完了報告に記載する

## ルール

- ソースコード、コメント、テスト名、文字列は英語で記述する。UI の文言はボードと DESIGN.md の英語の表記に従う
- 仕様を日本語のまま引用しない。英語に訳して DESIGN.md の節名を示す
- コードのコメントとテストの名前は、その処理が必要な条件と理由を記述し、発見の経緯を記述しない
- テストデータとサンプルには、架空の名前とパスを使用する
- 指示書の範囲外の機能を追加しない。DESIGN.md に記載のない動作が必要になったら、実装を止めてオーケストレーターに報告する
- 外部仕様（GitHub の API、Apple の API）を記憶だけで実装しない。公式ドキュメント、公開スキーマ、実データで確認し、完了報告に確認方法を記載する
- GitHub には書き込まない。確認の要求も読み取りだけにする
- エージェントが cargo を実行するときは、所有者が使用している `target/` と競合しないよう、別の `CARGO_TARGET_DIR` を指定する
- `scripts/dev-install.sh` と `scripts/dev-uninstall.sh` はエージェントが実行しない
- 画面に表示される計測を繰り返さない。確認は画面に表示しないモードで行う
- コミットはオーケストレーターの指示があるまで行わない
- 完了報告には、実装者が決めた点と、仕様の矛盾や不足を記載する。ビルドの警告の件数も記載する
