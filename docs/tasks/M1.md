# M1: デーモンの状態管理と CLI

Status: 完了

最初に CLAUDE.md、docs/DESIGN.md、docs/DEVELOPMENT.md を確認すること。挙動の正は DESIGN.md である。指示書と DESIGN.md が食い違う場合は、実装を止めてオーケストレーターに報告する。

## ゴール

GitHub に接続せずに、状態の規則を実際のデーモンと CLI で確認できる状態にする。テスト用の出来事をデーモンへ投入すると、`shiibar-gh list`、`activity`、`done`、`snooze` が DESIGN.md のとおりに動作する。

## 範囲

### 含める

- Cargo workspace、`rust-toolchain.toml`（Rust 1.99.1）、`deny.toml`、GitHub Actions の CI（macOS のランナー）
- crate 構成：`shiibar-gh-proto`（型と NDJSON）、`shiibar-gh-client`（ソケットのクライアント）、`shiibar-ghd`（デーモン）、`shiibar-gh`（CLI）
- ワイヤ形式のうち `token_set` と `token_test` を除くすべて。`subscribe` の `client` は必須で、省略すると `invalid` を返す
- ソケットの起動処理、SQLite の保存とスキーマ版の管理、DB を読めないときの待機と `reset`
- 行の状態遷移、残す行の整理、Reaction の行、監視開始より前の出来事、カードの表示判定と並び順、Needs action、バッジ、メニューバーの青い点
- スコープの追加、削除、enabled と disabled、PR のスコープの判定
- Snooze の毎朝の解除とまとめ通知、通知の要否の判定と配信の記録、`notify` イベントの配信

### 含めない

- GitHub の取得（REST、GraphQL、ポーリング、レート制限）。GitHub の値から状況アイコンへの変換も M2 で実装する
- Mentioned と Comment を同じ出来事と判定する処理。`dev_ingest` が渡す kind をそのまま使用する
- Keychain とトークン。`token set` と `token test` は M2 で実装する
- Swift アプリ、署名、リリース

スタブも作成しない。ただし `refresh` は、ワイヤ形式と CLI だけを実装し、M1 では何も取得せずに成功を返す。

## 確定事項

### 出来事の投入方法

cargo feature `dev-ingest` が有効なビルドにだけ、次のコマンドを含める。既定のビルドでは未知のコマンドとして拒否する。

| cmd | 内容 |
| --- | --- |
| `dev_ingest` | 引数 `ingest` で下の `Ingest` を受け取って適用し、`{"ok":true}` を返す。M2 の取得処理がデーモンの中核へ渡す型と同じ型である |
| `dev_clock_set` | 引数 `now`（epoch 秒）と `tz`（`Asia/Tokyo` のような IANA 名）で、デーモンの現在時刻とタイムゾーンを固定し、応答の前に定期処理を同期で 1 回実行する。ブラックボックス検証で Snooze の解除と 14 日の判定を確認するために使用する |

起動時の解除を検証できるよう、`dev-ingest` ビルドのデーモンは環境変数 `SHIIBAR_GH_DEV_NOW`（epoch 秒）と `SHIIBAR_GH_DEV_TZ`（IANA 名）で起動時の時刻とタイムゾーンを指定できる。指定した時刻は `dev_clock_set` と同じく固定する。

`Ingest` は次の値を持つ。出来事の分類（kind の決定）は取得処理の責務で、行の生成、未読、通知の判定はデーモンの中核の責務である。参加の有無、Bot、自分の投稿の判定は kind の決定に含まれる。そのため、中核は渡された kind を再判定せず、`Ingest` はこれらの判定に使用する値を持たない。

- `viewer`：自分のログイン名
- `missing_pr_ids`：id で取得して見つからなかった PR。読めなくなった PR として扱う
- `prs`：PR ごとに `id`、`owner`、`repo`、`number`、`url`、`title`、`author`、`base`、`head`、`state`（`open`、`merged`、`closed`）、`is_draft`、`review`、`checks`、`base_status`、`mergeable`（mergeStateStatus が CLEAN のときだけ真の真偽値）、`failed_check`、`changes_requested_by`、`updated_at`、`is_private`、`requested_me`（今も自分に依頼されているか）、`links`（キーは `review`、`checks`、`base` で、値は URL）
- `events`：出来事ごとに `id`、`pr_id`、`kind`、`occurred_at`、`url`、`actor`、`text`、`comment_id`
- `reactions`：自分のコメントごとに `comment_id`、`pr_id`、`url`、`text`、`comment_created_at`、`counts`（自分を除いた種類ごとの絶対件数）、`watching`（監視中か）

`failed_check`、`changes_requested_by`、`actor`、`text`、`comment_id` は `null` を許容する。時刻は epoch 秒である。要求の全体は次の形式である。

```json
{"cmd":"dev_ingest","ingest":{
  "viewer":"me",
  "missing_pr_ids":[],
  "prs":[{"id":"PR_1","owner":"example-org","repo":"app","number":1,"url":"https://github.example/1","title":"Fix","author":"me","base":"main","head":"fix","state":"open","is_draft":false,"review":"none","checks":"failed","base_status":"up_to_date","mergeable":false,"failed_check":"build","changes_requested_by":null,"updated_at":1800000000,"is_private":false,"requested_me":false,"links":{"review":"https://github.example/1/r","checks":"https://github.example/1/c","base":"https://github.example/1/b"}}],
  "events":[{"id":"E_1","pr_id":"PR_1","kind":"comment","occurred_at":1800000000,"url":"https://github.example/1#c","actor":"alice","text":"Looks good","comment_id":"C_1"}],
  "reactions":[{"comment_id":"C_2","pr_id":"PR_1","url":"https://github.example/1#d","text":"Done","comment_created_at":1800000000,"counts":{"THUMBS_UP":2},"watching":true}]
}}
```

未知の `kind`、または `prs` にも既知の PR にもない `pr_id` を含む `dev_ingest` は `invalid` を返し、全体を適用しない。

「監視開始より前の出来事」の判定はデーモンの中核が行う。中核はスコープごとに監視開始時刻を持ち、`occurred_at` がそれより前の出来事は行にしない。例外として、それより前の Review requested のうち、監視開始後にその PR を初めて取り込んだ時点で `requested_me` が真のものだけを行にし、通知しない。`occurred_at` が監視開始時刻以降の出来事は、PR を初めて検出した場合も通常の行として通知する。スコープの追加、enabled への切り替え、`reset` で監視開始時刻を設定するときは、そのスコープの PR の前回の値と Reaction の基準値を破棄する。M1 の `reset` のあとのスコープは Public だけである。Reaction の差分も中核が基準値と `watching` から求める。

`kind` は `review_requested`、`mentioned`、`comment`、`reply`、`added_to_merge_queue`、`removed_from_merge_queue`、`merged`、`closed`、`bot_comment` とする。`card.state_label` は `open`、`draft`、`mergeable`、`merged`、`closed` とし、`merged`、`closed`、`draft`、`mergeable`、`open` の順に該当するものを選択する。`counts` のキーは GraphQL の `ReactionContent` の値（`THUMBS_UP` など）とする。`row.kind` は、これに `checks_failed`、`conflicts`、`changes_requested`、`mergeable`、`reaction` を加えた値である。

`review` は `approved`、`review_required`、`changes_requested`、`none`、`checks` は `passed`、`in_progress`、`failed`、`none`、`base_status` は `up_to_date`、`behind`、`conflicts`、`none` とする。状態変化の行は、デーモンの中核が DESIGN.md の「状態変化の行」のとおりに生成する。本文は `Ingest` の PR の `failed_check` と `changes_requested_by` で受け取る。`actor` は `null` とする。`url` は `checks_failed` が `links.checks`、`conflicts` が `links.base`、`changes_requested` が `links.review`、`mergeable` が PR の `url` である。行の鍵は検知時刻を秒の単位で含むので、固定した時刻で同じ変化を 2 回検証するテストは、`dev_clock_set` で時刻を進める。

disabled のスコープに属する PR の `dev_ingest` は無視する。どのスコープにも属さない PR（未登録の owner の非公開 PR）も無視する。`list` と `activity` は disabled のスコープを除く。Needs action の絞り込みは PR 単位で行う。

### スコープと識別子

- スコープの識別子は owner のログイン名、または `public`
- `<pr>` は `owner/repo#number`、`<row>` は行の鍵とする
- PR の内部の鍵は GraphQL の node id とする

### 応答の項目

| 型 | 項目 |
| --- | --- |
| `scope` | `id`、`name`、`kind`（`org`、`user`、`public`。M1 では取得しないので owner のスコープは `null`）、`enabled`、`notify`、`color`（M3 で追加。値は DESIGN.md の「ワイヤ形式」）、`badge`、`dot`、`warnings`（M1 では空配列）、`updated_at`（そのスコープの PR または出来事を含む最後の `dev_ingest` の時刻。なければ `null`） |
| `card` | `id`、`pr`、`scope`、`title`、`url`、`author`、`author_avatar_url`（M3 で追加。`dev_ingest` の PR の省略可能な `author_avatar_url` から求める）、`mine`、`state_label`、`review`、`checks`、`base_status`、`base`、`head`、`snoozed`、`snoozed_until`、`added_at`、`links`、`rows` |
| `row` | `id`、`pr`、`pr_title`、`kind`、`class`（`needs_action`、`event`。やることではなくなった Review requested は `event`）、`text`、`counts`、`actor`、`url`、`occurred_at`、`unread`、`done` |
| `notification` | `id`、`type`（`single`、`summary`）、`scope`、`rows`、`pr`、`url`、`title`、`subtitle`、`body`。`summary` は 2 つの文面を `title` と `body` に設定し、`subtitle` は `null` とする |

`scope_changed` は `scope` の値が変化したときと、そのスコープのカードまたは行が変化したときに配信する。クライアントは `list` と `activity` で一覧を再取得する。

M3 で `subscribe` に `config_changed`（`key`、`value`）を、`settings_status` の `tokens` の要素に `warnings` を追加した（形は DESIGN.md の「ワイヤ形式」）。

Activity とカード内の行は `occurred_at` の降順に並べる。カードは `added_at` の降順に並べる。どちらも同時刻は `id` の昇順とする。

### Snooze の解除

- DB に最後の解除時刻 `last_release_at` を 1 つだけ保存する
- デーモンは 30 秒ごとの定期処理と起動時に、壁時計で現在時刻以前の最新の Return time を求める。その時刻が `last_release_at` より後なら、すべての Snooze を解除して `last_release_at` を更新する。スリープからの復帰も、この判定で処理する
- 初回起動時は `last_release_at` を現在時刻にする
- `snooze` の実行時は、先に未処理の解除を実行する。Return time を過ぎた後、次の定期処理より前に Snooze した PR を解除しないためである
- Return time の変更時は、先に未処理の解除を実行してから値を変更し、`last_release_at` を現在時刻にする
- Snooze 中に Done にした行はまとめ通知の対象から除く

### DB を読めないとき

待機の対象は、ファイルの破損で開けない場合、またはクエリが破損を報告した場合である。他プロセスのロックで開けない場合は待機状態にせず、エラーで終了する。DB のスキーマ版がプログラムより新しい場合もエラーで終了する。スキーマ版が古い場合は移行する。

### ファイルと定数

| 定数 | 値 |
| --- | --- |
| ソケット | 状態ディレクトリの `shiibar-ghd.sock`（0600） |
| ロック | 状態ディレクトリの `shiibar-ghd.lock`（0600）。二重起動は exit 1 |
| DB | 状態ディレクトリの `state.db`（`-wal` と `-shm` を含めて 0600） |
| 退避ファイル | `state.db.corrupt-<epoch 秒>`（0600）。`-wal` と `-shm` があれば `state.db.corrupt-<epoch 秒>-wal` と `-shm` に同時に移動する。SQLite は DB と同じ名前の `-wal` を対応するファイルとして開くので、新しい `state.db` の隣に古いファイルを残さない（確認：sqlite.org/howtocorrupt.html の 1.4 節、2.5 節） |
| 遅いクライアント | 送信キューが 256 件を超えたら切断する |
| 定期処理 | 30 秒 |
| デーモンの起動 | `--foreground` を指定すると前面で実行する。指定しない起動は使用法の誤りで exit 1 とする。ログは標準エラー出力に出力する |

## テスト

実装の前に、次の判定を DESIGN.md から表にして `crates/shiibar-ghd/tests/` のテーブル駆動テストにする。表の作成で新しい挙動が必要になったら、オーケストレーターに報告する。

- 行の状態遷移
- カードの表示判定
- Needs action とバッジ
- メニューバーの青い点
- 残す行の整理
- Reaction の行
- 監視開始より前の出来事
- Snooze の解除とまとめ通知
- 通知の判定、配信の記録、再接続時のまとめ
- スコープの判定と disabled の動作

統合テストの要件は次のとおりである。

- 実際のデーモンをソケット経由で操作する。順序の同期は `subscribe` で取り、sleep を使用しない
- 再起動後に Done、Snooze、未読、`seen_pending`、青い点、`last_release_at`、まとめ通知の記録、監視開始時刻、PR の前回の値、Reaction の基準値が復元され、配信済みの通知を再送しないことを確認する
- DB を読めないときに待機状態になり、DB を変更せず、`reset` で退避して通常の動作を始めることを確認する。待機状態への移行時と `reset` の時に購読者が切断され、再接続の `snapshot` で `db_unreadable` が正しいことも確認する
- スコープの削除時に購読者が切断され、再接続の `snapshot` にそのスコープが含まれないことを確認する
- `client:"app"` の購読者への書き込みの成功を配信とみなし、アプリが接続していない間の通知が再接続時にスコープごとのまとめ通知になることを確認する。Snooze の解除の対象の行も同じ 1 件に含まれることを確認する
- Activity の順序と絞り込み、終了コード、ファイルの権限、二重起動の防止、遅いクライアントの切断を確認する
- 既定のビルドが `dev_ingest` と `dev_clock_set` を拒否することを確認する
- テストは状態ディレクトリに一時ディレクトリを使用する。実際のホーム、ネットワーク、Keychain に触れない

## shiibar-cc の実装から引き継ぐ注意点

参考になる実装は `../shiibar-cc` にある。コピーではなく、次の点を確認して採用する。

- 起動処理は `info` で既存デーモンを確認し、応答がなければ古いソケットを削除してから bind する。応答が遅いだけのデーモンと二重起動しないよう、ファイルロックも併用する
- ソケットファイルは listen より先に現れる。テストの起動待ちはファイルの存在ではなく接続の成功で判定する
- 状態の適用とクライアントへの配信は、適用と保存が完了してから行う。`subscribe` の開始時は、スナップショットの取得と購読の登録を同じロックの中で行う
- 遅いクライアントは切断する。クライアントは再接続とスナップショットで回復する
- 長い `snapshot` を受信するので、クライアントは 1 行が複数回の読み取りに分かれても処理できるようにする
- ワイヤの型を保存型と共有しない。未知の値を丸めて保存すると、Done と Snooze は復元できない
- クライアントが受信する enum には未知の値を許容する。`Request` には許容しない
- ファイルの権限は明示する。umask に任せない
- 状態ディレクトリの解決は 1 か所にまとめる
- GitHub Actions の `uses:` はフルコミット SHA で固定する
