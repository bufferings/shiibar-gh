# M1: デーモンの状態管理と CLI

Status: 未着手

最初に CLAUDE.md、docs/DESIGN.md、docs/DEVELOPMENT.md を確認すること。挙動の正は DESIGN.md である。指示書と DESIGN.md が食い違う場合は、実装を止めてオーケストレーターに報告する。

## ゴール

GitHub に接続せずに、状態の規則を実際のデーモンと CLI で確認できる状態にする。テスト用の出来事をデーモンへ投入すると、`shiibar-gh list`、`activity`、`done`、`snooze` が DESIGN.md のとおりに動作する。

## 範囲

### 含める

- Cargo workspace、`rust-toolchain.toml`（Rust 1.99.1）、`deny.toml`、GitHub Actions の CI（macOS のランナー）
- crate 構成：`shiibar-gh-proto`（型と NDJSON）、`shiibar-gh-client`（ソケットのクライアント）、`shiibar-ghd`（デーモン）、`shiibar-gh`（CLI）
- ワイヤ形式のうち `token_set` と `token_test` を除くすべて。`subscribe` には `client`（`app` または `cli`）を追加する
- ソケットの起動処理、SQLite の保存とスキーマ版の管理、DB を読めないときの待機と `reset`
- 行の状態遷移、残す行の整理、Reaction の行、検出前の出来事、カードの表示判定と並び順、Needs action、バッジ、メニューバーの青い点
- スコープの追加、削除、enabled と disabled、PR のスコープの判定
- Snooze の毎朝の解除とまとめ通知、通知の要否の判定と配信の記録、`notify` イベントの配信

### 含めない

- GitHub の取得（REST、GraphQL、ポーリング、レート制限）。GitHub の値から状況アイコンへの変換も M2 で実装する
- Mentioned と Comment を同じ出来事と判定する処理。`dev_ingest` が渡す kind をそのまま使用する
- Keychain とトークン。`token set` と `token test` は M2 で実装する
- Swift アプリ、署名、リリース

スタブも作成しない。ただし `refresh` は、ワイヤ形式と CLI だけを実装し、M1 では何も取得せずに成功を返す。

## 確定事項

### 出来事の投入方法

cargo feature `dev-ingest` が有効なビルドにだけ、次のコマンドを含める。既定のビルドでは未知のコマンドとして拒否する。

| cmd | 内容 |
| --- | --- |
| `dev_ingest` | 下の `Ingest` を適用する。M2 の取得処理がデーモンの中核へ渡す型と同じ型である |
| `dev_clock_set` | 引数 `now`（epoch 秒）と `tz`（`Asia/Tokyo` のような IANA 名）で、デーモンの現在時刻とタイムゾーンを固定し、応答の前に定期処理を同期で 1 回実行する。ブラックボックス検証で Snooze の解除と 14 日の判定を確認するために使用する |

起動時の解除を検証できるよう、`dev-ingest` ビルドのデーモンは環境変数 `SHIIBAR_GH_DEV_NOW`（epoch 秒）と `SHIIBAR_GH_DEV_TZ`（IANA 名）で起動時の時刻とタイムゾーンを指定できる。

`Ingest` は次の値を持つ。出来事の分類（kind の決定）は取得処理の責務で、行の生成、未読、通知の判定はデーモンの中核の責務である。

- `viewer`：自分のログイン名
- `missing_pr_ids`：id で取得して見つからなかった PR。読めなくなった PR として扱う
- `prs`：PR ごとに `id`、`owner`、`repo`、`number`、`url`、`title`、`author`、`base`、`head`、`state`（`open`、`merged`、`closed`）、`is_draft`、`review`、`checks`、`base_status`、`mergeable`、`participating`、`updated_at`、`is_private`、`requested_me`（今も自分に依頼されているか）、`links`（Review、Checks、Base の URL）
- `events`：出来事ごとに `id`、`pr_id`、`kind`、`occurred_at`、`url`、`actor`、`actor_is_bot`、`text`、`comment_id`
- `reactions`：自分のコメントごとに `comment_id`、`pr_id`、`url`、`text`、`counts`（自分を除いた種類ごとの絶対件数）、`watching`（監視中か）

「検出前の出来事」の判定はデーモンの中核が行う。中核は PR ごとの検出時刻を持ち、それより前の出来事は行にしない。その時点で `requested_me` が真の Review requested だけを行にし、通知しない。スコープの追加、enabled への切り替え、`reset` のあとも基準を再設定する。M1 の `reset` のあとのスコープは Public だけである。Reaction の差分も中核が基準値と `watching` から求める。

`kind` は `review_requested`、`mentioned`、`comment`、`reply`、`added_to_merge_queue`、`removed_from_merge_queue`、`merged`、`closed`、`bot_comment` とする。`card.state_label` は `open`、`draft`、`mergeable`、`merged`、`closed` とする。`counts` のキーは GraphQL の `ReactionContent` の値（`THUMBS_UP` など）とする。`reactions` の各要素には `comment_created_at` を含める。`row.kind` は、これに `checks_failed`、`conflicts`、`changes_requested`、`mergeable`、`reaction` を加えた値である。

`review` は `approved`、`review_required`、`changes_requested`、`none`、`checks` は `passed`、`in_progress`、`failed`、`none`、`base_status` は `up_to_date`、`behind`、`conflicts`、`none` とする。状態変化の行（Checks failed、Conflicts、Changes requested、Mergeable）は、デーモンの中核が自分の PR について前回の値との差分から生成する。Checks failed の本文は失敗したチェックの名前、Changes requested の本文はレビュアーのログイン名とし、`Ingest` の PR の `failed_check` と `changes_requested_by` で受け取る。

disabled のスコープに属する PR の `dev_ingest` は無視する。`list` と `activity` は disabled のスコープを除く。Needs action の絞り込みは PR 単位で行う。

### スコープと識別子

- スコープの識別子は owner のログイン名、または `public`
- `<pr>` は `owner/repo#number`、`<row>` は行の鍵とする
- PR の内部の鍵は GraphQL の node id とする

### 応答の項目

| 型 | 項目 |
| --- | --- |
| `scope` | `id`、`name`、`kind`（`org`、`user`、`public`。M1 では取得しないので owner のスコープは `null`）、`enabled`、`notify`、`badge`、`dot`、`warnings`、`updated_at` |
| `card` | `id`、`pr`、`scope`、`title`、`url`、`author`、`mine`、`state_label`、`review`、`checks`、`base_status`、`base`、`head`、`snoozed`、`snoozed_until`、`added_at`、`links`、`rows` |
| `row` | `id`、`pr`、`pr_title`、`kind`、`class`（`needs_action`、`event`。やることではなくなった Review requested は `event`）、`text`、`counts`、`actor`、`url`、`occurred_at`、`unread`、`done` |
| `notification` | `id`、`type`（`single`、`summary`）、`scope`、`rows`、`pr`、`url`、`title`、`subtitle`、`body` |

`scope_changed` は `scope` の値が変化したときと、そのスコープのカードまたは行が変化したときに配信する。クライアントは `list` と `activity` で一覧を再取得する。

Activity は `occurred_at` の降順に並べる。同時刻は `id` の昇順とする。

### エラー

応答の失敗は `{"ok":false,"code":"...","error":"..."}` とする。`code` は `not_found`、`invalid`、`internal` のいずれかである。

| 状況 | 応答 | CLI の終了コード |
| --- | --- | --- |
| `done`、`undone`、`snooze`、`unsnooze`、`status`、`open` の対象がない。整理済みの行、未知のスコープも含む | `not_found` | 2 |
| `seen` の id の一部が存在しない | 存在する分を適用して ok | 0 |
| イベントの行への `done` | ok、変化なし | 0 |
| 不正な設定値、`public` の `scope add`、スコープの重複追加、`public` の `scope remove` | `invalid` | 1 |
| DB を読めない間の `reset`、`info`、`subscribe`、`shutdown` 以外のコマンド | `internal` | 1 |
| DB を読めるときの `reset`（`saved state is readable; nothing to reset`） | `invalid` | 1 |
| やることではなくなった Review requested の行への `done` | ok、変化なし | 0 |
| CLI の使用法の誤り | — | 1 |

### Snooze の解除

- DB に最後の解除時刻 `last_release_at` を 1 つだけ保存する
- デーモンは 30 秒ごとの定期処理と起動時に、壁時計で現在時刻以前の最新の Return time を求める。その時刻が `last_release_at` より後なら、すべての Snooze を解除して `last_release_at` を更新する。スリープからの復帰も、この判定で処理する
- 初回起動時は `last_release_at` を現在時刻にする
- Return time の変更時は、先に未処理の解除を実行してから値を変更し、`last_release_at` を現在時刻にする
- Snooze 中に Done にした行はまとめ通知の対象から除く

### DB を読めないとき

待機の対象は、ファイルの破損で開けない場合、またはクエリが破損を報告した場合である。他プロセスのロックで開けない場合は待機状態にせず、エラーで終了する。DB のスキーマ版がプログラムより新しい場合もエラーで終了する。スキーマ版が古い場合は移行する。

### ファイルと定数

| 定数 | 値 |
| --- | --- |
| ソケット | 状態ディレクトリの `shiibar-ghd.sock`（0600） |
| ロック | 状態ディレクトリの `shiibar-ghd.lock`（0600）。二重起動は exit 1 |
| DB | 状態ディレクトリの `state.db`（`-wal` と `-shm` を含めて 0600） |
| 退避ファイル | `state.db.corrupt-<epoch 秒>`（0600） |
| 遅いクライアント | 送信キューが 256 件を超えたら切断する |
| 定期処理 | 30 秒 |
| デーモンの起動 | `--foreground` を指定すると前面で実行する |

## テスト

実装の前に、次の判定を DESIGN.md から表にして `crates/shiibar-ghd/tests/` のテーブル駆動テストにする。表の作成で新しい挙動が必要になったら、オーケストレーターに報告する。

- 行の状態遷移
- カードの表示判定
- Needs action とバッジ
- メニューバーの青い点
- 残す行の整理
- Reaction の行
- 検出前の出来事
- Snooze の解除とまとめ通知
- 通知の判定、配信の記録、再接続時のまとめ
- スコープの判定と disabled の動作

統合テストの要件は次のとおりである。

- 実際のデーモンをソケット経由で操作する。順序の同期は `subscribe` で取り、sleep を使用しない
- 再起動後に Done、Snooze、未読、`seen_pending`、青い点、`last_release_at`、まとめ通知の記録が復元され、配信済みの通知を再送しないことを確認する
- DB を読めないときに待機状態になり、DB を変更せず、`reset` で退避して通常の動作を始めることを確認する
- `client:"app"` の購読者への書き込みの成功を配信とみなし、アプリが接続していない間の通知が再接続時にスコープごとのまとめ通知になることを確認する
- Activity の順序と絞り込み、終了コード、ファイルの権限、二重起動の防止、遅いクライアントの切断を確認する
- 既定のビルドが `dev_ingest` と `dev_clock_set` を拒否することを確認する
- テストは状態ディレクトリに一時ディレクトリを使用する。実際のホーム、ネットワーク、Keychain に触れない

## shiibar-cc の実装から引き継ぐ注意点

参考になる実装は `../shiibar-cc` にある。コピーではなく、次の点を確認して採用する。

- 起動処理は `info` で既存デーモンを確認し、応答がなければ古いソケットを削除してから bind する。応答が遅いだけのデーモンと二重起動しないよう、ファイルロックも併用する
- ソケットファイルは listen より先に現れる。テストの起動待ちはファイルの存在ではなく接続の成功で判定する
- 状態の適用とクライアントへの配信は、適用と保存が完了してから行う。`subscribe` の開始時は、スナップショットの取得と購読の登録を同じロックの中で行う
- 遅いクライアントは切断する。クライアントは再接続とスナップショットで回復する
- 長い `snapshot` を受信するので、クライアントは 1 行が複数回の読み取りに分かれても処理できるようにする
- ワイヤの型を保存型と共有しない。未知の値を丸めて保存すると、Done と Snooze は復元できない
- クライアントが受信する enum には未知の値を許容する。`Request` には許容しない
- ファイルの権限は明示する。umask に任せない
- 状態ディレクトリの解決は 1 か所にまとめる
- GitHub Actions の `uses:` はフルコミット SHA で固定する
