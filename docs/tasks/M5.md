### DB と移行

- スキーマは版 5。0.2（版 4）の DB は起動時に移行する。Todo と Done の列（`owner_events.todo`、`pr_rows.seen_pending`、`done`、`todo_auto`、`todo_manual`）を削除するほかは、すべての表とデータをそのまま引き継ぐ。PR の前回の値、Reaction の基準値、通知の配信の記録、整理済みの印、通知 API の since も含む（DESIGN.md「状態の保存」）
- 移行の手順。1 つのトランザクションの中で次を順に行う
  1. `owner_events.todo` を削除する
  2. `pr_rows.seen_pending`、`pr_rows.done`、`pr_rows.todo_auto`、`pr_rows.todo_manual` を削除する
  3. `prs.created_at`（null 可）を追加する。値は次の取得で埋まり、それまでワイヤの `created_at` は `null` である
  4. `user_version` を 5 にする
  5. コミットする。途中で失敗したらロールバックし、版 4 のまま「DB を読めないとき」の状態にする（0.2 の「DB を読めない」と同じ扱い）
- 0.2 で通知だけから取り込んだ PR と行は移行で消さない。repo#number → id の対応は、保存した PR（prs 表の owner、repo、number）から求める（「PR の識別」）
- 0.1（版 3 以前）の DB は M4 のまま「DB を読めないとき」の状態にする。版がプログラムより新しい DB は M1 のままエラーで終了する
- Keychain の項目（service `shiibar-gh`、account `accounts`、版 2）は変更しない
- レビュー待ちの状態は PR の最新の値（レビューの依頼と自分のレビューの有無）から表示のたびに求め、列に保存するかは実装者が決める。開いている間に表示したカードの集合と、取得の最初の失敗の時刻は保存しない

### 取得

- 1 回の取得：アカウントの定期取得（全 owner の検索と状況の取得、および通知の確認）を 1 回の取得として扱い、その終了時刻から次の取得の時刻を 1 つ決める。Reaction の取得は 0.2 のまま別の時刻で動かし、成功と失敗の判定にも `updated_at` にも関係させない。通知の確認は、X-Poll-Interval が経過していなければその回は省き、省いた回も成功として扱う（DESIGN.md「取得の成功と失敗」）
- 再試行：成功なら設定の間隔。失敗なら 5、10、20、40 秒と延ばし、40 秒のあとは 40 秒を繰り返す。どの待ち時間も設定の間隔を超えない。再試行は、失敗した owner だけでなくアカウントの取得全体をやり直す
- `refresh`：いつでもすぐ実行し、通常の 1 回の取得として扱う。成功すれば失敗の回数を 0 に戻し、`updated_at` を進め、次の定期取得をその終了時刻から設定の間隔のあとにする。失敗すれば失敗の回数を 1 つ進め、最初の失敗なら 5 分の起点になる
- 5 分の帯：`fetch_failed` の警告は、最初の失敗から 5 分たっても成功していないときに付け、成功で除く。`until` は次の再試行の時刻。最初の失敗の時刻は保存せず、デーモンの再起動で消える。上限による停止、401、トークンなし、Keychain を読めない間は取得していないので `fetch_failed` を付けない（それぞれの警告を表示する）。停止を始めた時点で失敗の回数と最初の失敗の時刻は消え、再開後の最初の失敗から再び数える。帯の文言（`retrying in N min` の N の求め方）は 0.2 の形式のまま。Reaction の取得の失敗は判定に含めない
- 本文が空、または解釈できない GraphQL の 200 の応答は、ネットワークの失敗と同じ扱い（再試行の対象）にする。REST の扱い（空の本文を null として受け入れる）は変更しない
- `updated_at` はそのアカウントの取得が最後に成功して終わった時刻。失敗が続く間は進まない。成功がなければ `null`（アプリは `Not updated yet`）
- 通知 API：通知された PR のうち、repo#number → id の対応をすでに持つ PR だけを再取得の対象にする。対応は保存した PR（prs 表の owner、repo、number）から求め、通知から取得した分だけの今の対応表（`fetch.pr_ids`）は使用しない。対応のない PR は無視し、id を引かない（今の未知の PR の id を引く処理は削除する）。If-Modified-Since と X-Poll-Interval の扱いは M4 のまま
- SSO：`X-GitHub-SSO` の `organizations=` の id が登録済みの owner の `github_id` に一致したときだけ `sso_required` を付ける。一致しなければ何もしない。1 つの organization への 403（URL だけの形）は、owner ごとの要求（検索）で受けたときはその owner の `sso_required` とし、複数の owner にまたがる要求（状況の取得、通知）で受けたときはその取得の失敗として扱う（警告なし、再試行と 5 分の帯の対象）。名前なしの `sso_required` は廃止する（DESIGN.md「トークン」）
- `createdAt` を PR の取得に追加する

### 行と既読

- 行の生成時に決めるのは `notify`（表の Notify、Exclusions、Skip draft pull requests から）だけである。List は表示時に今の表と Exclusions から求める（M4 のまま）
- 既読：`read`（行 id の配列）は指定した行の未読を下ろす。`read_all`（アカウント）は、Snooze 中の PR の行を除くそのアカウントのすべての行（Hidden や List オフで表示しない行を含む）の未読を下ろす。`seen` は削除する。`popover_opened`／`popover_closed` は残し、メニューバーの青い点と行の整理、カードの消滅の反映の時点にだけ使用する（行の既読は変更しない）。既読になった行の整理（PR ごとに新しい 3 件）とカードの消滅は、ポップオーバーを閉じたときに反映する
- 開いている間に表示したカードの保持（DESIGN.md「カードが出る・消える条件と監視期間」）：デーモンはアカウントごとに「開いている間に表示したカードの PR の集合」を持つ。`popover_opened` のあと、`list` の応答に含めた PR をこの集合に加え、集合にある PR は消える条件を満たしても `list` に含め続ける。`popover_closed`、`app` の接続の切断、デーモンの起動で集合を空にする。この集合は保存しない。`pr_count` は `list` に含めるカードの数とし、同じ集合を使用する。`review_count` は PR の状態なので集合で保持しない
- レビュー待ちの判定（DESIGN.md「レビュー待ちの定義」）。M4 の「今もやることか」の判定（engine.rs の、表示される最新の Review requested の行を条件にする判定）は流用しない
  - 自分宛ての依頼は、reviewRequests に自分がいれば数える。行の有無と、Review requested の List のオンとオフは条件にしない
  - チーム宛ての依頼は、その owner の Review requested to my team の List がオンのときだけ数える
  - 自分宛てもチーム宛ても、最新の依頼のあとに自分のレビューがあれば数えない。レビューは今の取得（fetch.rs の `reviews(first: 100)`、author を含む）から判定する。最新の依頼の時刻は Review requested の行（記録だけの行を含む）の時刻で判定し、行がなければ自分のレビューが 1 つでもあれば数えない
  - 依頼した人の Exclusions（Hidden または List only なら数えない）は、その PR の最新の Review requested の行（自分宛ての依頼では自分宛ての行、チーム宛ての依頼ではチーム宛ての行。記録だけの行を含む）の actor で判定する。行がなければ（依頼者が分からなければ）数える
  - Snooze 中、読めなくなった PR、Hidden のリポジトリの PR は数えない。レビュー待ちの PR はカードを残す
- `awaiting_review` と `review_count` は表示のたびに（`list`、`account_changed` のたびに）求める。disabled の owner は 0、アカウントの値は owner の和（DESIGN.md「カードの状態」）
- 監視開始より前の出来事の例外（今も続くレビュー依頼は未読の行にする）は M4 のまま

### 表示（アプリ）

- ボード Main.html と Activity.html に従う。チップの行はチップごとの固有の幅で左寄せにし、ポップオーバーやウインドウの幅に合わせて伸ばさない
- Group by、並び、絞り込みの選択、折りたたみ、Activity の owner の選択、ウインドウの位置と Keep on top はアカウントごとに UserDefaults に保存する。折りたたみは Group by の値とセクションの鍵の組ごとに保存する。検索の文字と `+ N more PRs` の展開は保存しない
- 絞り込みと検索の場所（DESIGN.md「絞り込みの意味」）：アプリは `list` と `activity` を絞り込み（`filter`、`owner`、`owners`）も `search` も付けずに取得し、チップ、owner のボタン、検索、Group by、並び、`+ N more PRs` の計算をすべてアプリで行う。ワイヤの `filter` と `search` は CLI のためだけに残し、CLI ではデーモンが判定する。検索の一致の規則は Rust と Swift で同じにし、DESIGN.md「絞り込みの意味」の例を両方のテストで使用する
- 並びと Group by の計算、`+ N more PRs` の畳み方、検索の一致、Status と Involvement の分類は UI から分離して `swift test` で確認する
- Group by `None`：見出しなしの 1 本の一覧。開いている PR を先に、Merged と Closed をあと、その次に `+ N more PRs`、最後に Snoozed セクション。選択はカードの見出し、行、`+ N more PRs`、Snoozed の見出しの順。None には折りたたみがない（DESIGN.md「PRs タブのセクション」）
- カードのないセクション：絞り込みと検索のあとにカードがないセクションは表示しない。見出しの数は絞り込みと検索に依存しない。チップと検索は Snoozed セクションにも適用し、見出しの `until` は残す
- `+ N more PRs`：ポップオーバーを開いた時点と新しい PR が現れた時点で畳むかどうかを決め、開いている間は畳まずに表示した PR を畳まない。閉じたときに判定をやり直す。常時表示ウインドウはフォーカスが外れたときにやり直す。検索の文字があるときは畳まない。チップだけのときは畳む
- `All owners`：記憶した選択が空のときオンに表示する。owner を 1 つでもオンにするとオフ。すべての owner を個別にオンにしてもオフのまま。記憶した選択の中の削除済みと disabled の owner は無視する
- ⇧R と `Mark all as read`：表示中のタブに今表示している行（チップ、検索、owner のボタンを適用したあと。折りたたんだセクションの行は含め、Snoozed セクションの行は含めない）の id を `read` に列挙して送る。`read_all` は使用しない
- 開いたときの既読：⏎、ダブルクリック、右クリックの `Open on GitHub` では、アプリが URL を開くとともに `read` を送る。ワイヤの `open` と CLI の `open <row>` は既読にしない
- 右クリック：その項目を選んで（行なら既読にして）からメニューを表示する
- 検索欄とキー（DESIGN.md「キーボード」）：開いたときに検索欄にフォーカスは移らない。⌘F で検索欄に移る。検索欄で Esc は、文字があれば消して一覧に戻り、空なら一覧に戻るだけ（ポップオーバーは閉じない）。↓ も一覧に戻る。検索欄にいる間、⇧R と S は文字として入力する。検索の文字はポップオーバーを閉じたとき（ウインドウは閉じたとき）に消し、PRs と Activity で別に持つ
- キーのヒント：何も選択していないとき、セクションの見出し、`+ N more PRs` でも ⇧R と ⌘F を表示する（DESIGN.md「キーボード」の表）
- 移行直後の `created_at` が `null` のカードは、3 行目を `by alice · updated 2h ago` にする
- メニューバーのアイコンのアクセシビリティの文言は `N review requests`（1 なら `1 review request`、0 なら `No review requests`）。今の `N Todo` を置き換える
- 文字の大きさ：`text_size` を本文の大きさとし、ほかの文字、行の高さ、アバターを 12 に対する比率で連動させる。ポップオーバーは幅も比率で連動させる。常時表示ウインドウは記憶した大きさを優先し、内容だけを比率で連動させる。メニューバーのアイコンと設定画面には適用しない。`config_changed` で即時に反映する。⌘=（⌘+ も）、⌘−、⌘0 は `config_set` を送る。18 での ⌘= と 9 での ⌘− は何もしない（要求を送らない）。設定画面のステッパーの欄は 9〜18 の外の値を受け付けず、範囲外の入力には "Enter a number from 9 to 18" を表示する
- 要求の回数（段階 1 のレビューの A5）：行を選ぶたびに `read`、`account_changed`、`list`／`activity` の取り直しが起きる。アプリは `read` を送った行の未読を自分で消し、`account_changed` による取り直しはまとめて（短い遅延で 1 回に）行い、選択は行の id で再設定する。実装者が実装して、遅延の値と方法を完了報告に記載する
- Keep on top は NSPanel の `level` を切り替える。値は UserDefaults に保存し、次に開いたときに復元する
- クリックの選択、ダブルクリックの開く、右クリックのメニューはカードの見出しと行で同じ作りにする。チェックボックスは削除する
- 見出しの `API 25%` は GraphQL と REST の使用率の高い方。`rate_limit` が `null` なら `API –`。80% 以上は警告の色。マウスを乗せると両方の数
- Add account… と Edit… のシートは、開いた時点でテスト結果の領域を確保し、結果が出るまで項目名を薄く表示する（Sheets.html）

### ワイヤ形式と CLI

## 確認した外部仕様

実装前に次を確認し、確認方法を完了報告に記載する。確認できないものは DESIGN.md の「未決」に残す。

- `PullRequest.createdAt` が `DateTime!` で非推奨でないこと（公開スキーマ）
- 通知 API の応答で、既知の PR の判定に使用する `subject.url` の形（`.../pulls/{number}`）：確認済み。REST のドキュメントは `subject.url` を string とだけ記載するが、0.2 の `crates/shiibar-ghd/src/convert.rs` の `pull_from_url` がこの形を解釈し、所有者の環境で通知から PR を取り込めていた（0.2.0 のフィードバック。renovate の PR が通知から取り込まれた）
- レビューを投稿すると GitHub が reviewRequests から自分（またはチーム）を除くか：確認していない。前提にせず、レビュー待ちの条件「最新の依頼のあとに自分のレビューがない」で補う（DESIGN.md「レビュー待ちの定義」）
- NSPanel の `level` を実行中に切り替えたときの動作：Apple のドキュメント（NSWindow.level、NSPanel.isFloatingPanel）は値の意味だけを記載する。今のウインドウは `isFloatingPanel = true` と `.utilityWindow` も指定しているので、オフにしたときの動作を段階 6 の実機の確認項目にする
- SwiftUI で文字の大きさを比率で連動させる方法（`dynamicTypeSize` ではなく固定の pt を使用しているため、実装者が方法を決めて記載する）
- SQLite のスキーマ変更（列の削除）を 1 つのトランザクションで行う方法（`ALTER TABLE DROP COLUMN` の対応版。rusqlite が同梱する SQLite の版で確認する）

## ルール

- ソースコード、コメント、テスト名、文字列は英語で記述する。UI の文言はボードと DESIGN.md の英語の表記に従う
- 仕様を日本語のまま引用しない。英語に訳して DESIGN.md の節名を示す
- 指示書の範囲外の機能を追加しない。DESIGN.md に記載のない動作が必要になったら、実装を止めてオーケストレーターに報告する
- 外部仕様（GitHub の API、Apple の API）を記憶だけで実装しない。公式ドキュメント、公開スキーマ、実データで確認し、完了報告に確認方法を記載する
- 依存のパッケージ（Swift Package と crate）は、公開から 7 日以上たった版だけを使用する
- エージェントが cargo を実行するときは、所有者が使用している `target/` と競合しないよう、別の `CARGO_TARGET_DIR` を指定する
- `scripts/dev-install.sh` と `scripts/dev-uninstall.sh` はエージェントが実行しない
- コミットはオーケストレーターの指示があるまで行わない
- 完了報告には、実装者が決めた点と、仕様の矛盾や不足を記載する
