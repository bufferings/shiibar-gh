# M6: 0.3.0 の感想への対応（0.4）

Status: 完了（0.4.0 を 2026-11-13 に公開）。段階 6（所有者の確認）は公開のあとに行う

最初に CLAUDE.md、docs/DESIGN.md、docs/DEVELOPMENT.md、docs/tasks/M1.md〜M5.md と、docs/design/ のすべてのボードを確認すること。挙動の正は DESIGN.md、見た目の正は docs/design/ である。M1〜M5 のブリーフは完了した時点の記録で、DESIGN.md と食い違う箇所は DESIGN.md が優先する。0.3 から 0.4 で変更した範囲は `git diff main -- docs/DESIGN.md` で確認できる。指示書と DESIGN.md が食い違う場合は、実装を止めてオーケストレーターに報告する。

## ゴール

所有者が 0.3.0 を使用して挙げた 22 件の感想に、1 つの版で応える。中心は、アプリが更新を知らせ、カードの配置と順番は利用者が決める形への変更である。ポップオーバーのタブを All、Review、Mine の 3 つにし、Review（`Doing`、`Todo`、`Waiting`、`Done`）と Mine では利用者がドラッグ＆ドロップ、右クリック、キーでカードの区画と順位を決める。カードの表示と既読を連動させず、カードを一覧から除くのは Dismiss（期限付きで Restore できる）だけにする。Snooze と Exclusions は Mute（リポジトリ、利用者、PR 1 枚）に置き換え、Activity タブとメニューバーの数字は廃止する。あわせて、マージした PR の Closed の行、アプリが CPU を使用し続ける不具合、PR が多いアカウントで 502 が続く問題（要求の分割、要求ごとの再試行、部分的な結果の反映、要求ごとのログ）を修正する。0.3 と 0.2 のデータは、アカウントとトークンだけを引き継ぐ。

### 失敗した要求のログの試作

所有者の作業メモに、失敗した要求のログの試作の差分（リポジトリには未適用）がある。オーケストレーターが段階 2 の開始時に実装者へ渡す。実装者はこれを基にしてよく、使用するかどうかを完了報告に記載する。内容は次のとおりである。

- `crates/shiibar-ghd/src/fetch.rs`：`Run::gql` と `Run::rest` で所要時間を計り、失敗した要求ごとに `request of <login> failed after <ms> ms: <要求> (<件数>): <エラー>` を info で記録する。`describe_query` がクエリの名前と件数（`ids: N` または `variables: N`）を求める。REST の 404 は debug
- `crates/shiibar-ghd/src/github.rs`：エラーの文言に状態コードと `x-github-request-id` を含める
- `crates/shiibar-ghd/src/logging.rs`：すべての行の先頭に `jiff::Zoned::now()` の時差付きのローカル時刻（`%Y-%m-%d %H:%M:%S%:z`）を付ける。`jiff` はすでに shiibar-ghd の依存である
- `crates/shiibar-ghd/tests/fetch_black_box.rs`：`Status` の要求に 502 を返し、ログの行の形と時刻の長さを確かめるテスト

試作は 0.3 のコード（状況の要求は 100 件、要求の失敗でアカウントの取得全体を止める）に対するもので、0.4 の分割と再実行には合わせていない。行の形は DESIGN.md「ログ」に従う。

## 実装の要点

DESIGN.md の規則をここでは繰り返さない。各項目は、どこに何を作成するかだけを示す。

### DB と移行

- スキーマは版 6。`crates/shiibar-ghd/src/store.rs` の `SCHEMA_VERSION` を 6 にし、版 6 の表を新しく定義する。今の `SCHEMA_V5` と `MIGRATE_V4_TO_V5` は、版 5 と版 4 からの移行の判定のためだけに残すか削除するかを実装者が決める
- 版 5 と版 4 の DB は、1 つのトランザクションで、アカウントの表から引き継ぐ値を残し、ほかの表を削除し、版 6 の表を作成し、`user_version` を 6 にする。失敗したらロールバックし、元の版のまま「DB を読めないとき」の状態にする（DESIGN.md「0.3 と 0.2 からの更新」）。版 3 以下は M4 のまま「DB を読めないとき」、版がプログラムより新しい DB は M1 のままエラーで終了する
- 引き継ぐ値は DESIGN.md のとおりアカウントの id、login、色、登録の順（今の `accounts.seq`）である。今の `accounts` の表のほかの列（`token`、`updated_at`、`dot`、`teams`、`graphql_limit`、`rest_limit`、`stopped_until`、`fetch`。`crates/shiibar-ghd/src/model.rs` の `AccountRec`、`TokenRec`、`FetchRec`）は引き継がない
- 移行のあとは DB にアカウントがあるので、デーモンは最初の取得で Keychain を読み込む（「Keychain を読めないとき」）。Keychain の項目（service `shiibar-gh`、account `accounts`、版 2）は変更しない
- 版 6 が保存するもの：DESIGN.md「状態の保存」の列挙のとおり。新しく必要な主なものは、配置（タブ、区画、順位、クローズ前の区画と順位）、マージまたはクローズを検知した時刻、Dismiss の時刻と自動の Dismiss をしない印、Dismiss の記録（PR の id と記録した時点の `updatedAt`）、Mute の 3 種類（アカウントごと）、Checks の前回の観測値と前回の確定した結果と、そのときの head のコミット、PR ごとの自分または自分のチームへの最新の依頼の時刻（行とは別。「レビュー待ちの定義」）、失敗した要求の記録、PR ごとに削除した行の鍵、owner ごとの最後に取得に成功した時刻。列と表の形は実装者が決め、完了報告に記載する
- 取得の最初の失敗の時刻は保存しない（M5 のまま）
- アプリは 0.3 以前の UserDefaults の画面の状態を読み込まない。キーの名前の付け方（新しい接頭辞など）は実装者が決め、完了報告に記載する

### デーモン（状態と規則）

- 主な変更先は `crates/shiibar-ghd/src/engine.rs`（カードと行の規則、通知）、`engine/fetch_api.rs`（取得の計画と反映、警告）、`engine/accounts.rs`（owner、出来事の表、Mute の一覧）、`model.rs`、`plan.rs`、`daemon.rs`（要求の処理と保存）、`server.rs`
- 削除する：Snooze（`end_snooze`、`release_if_due` の Snooze の部分、Snoozed の扱い）、Exclusions（`repo_exclusion`、`user_exclusion`、`exclusion`、`repo_hidden`）、開いている間に表示したカードの保持（`is_held`、`on_screen`）、既読による表示の判定（`would_show`、`shows_unsnoozed` の未読と日数の条件）、PR ごとの既読の行の整理（新しい 3 件）、`review_count`
- 追加する：配置と順位の規則（「カードの状態」の表のすべての行。閉じた PR を新しく発見したときと、閉じた配置なしの PR への `Add to Review`／`Add to Mine` で `Done` に配置する 2 行を含む）、`Done` への自動の移動を状況の取得で検知した時点の 1 回だけ行い、再オープンによる `Done` からの復帰も状況の取得に従わせること（Reopened の行とは独立。「Review」）、利用者による `Done` への移動と `Done` からの移動（開いている PR とマージまたはクローズされた PR の両方。`Done` に入った時刻の順。「Review」「Mine」）、`place` の位置の既定値と `invalid` の条件（`done` への配置での `before` と `at`。「ワイヤ形式」の `place` の段落）、カードの `auto_dismiss_at`、Mute の対象のカードと順位（`placement.position` は Mute の対象を末尾にした表示の順、自動の追加は Mute の対象でないカードの末尾、Mute の対象を `before` に指定した `place` は `invalid`。「Review」「ワイヤ形式」）、Dismiss と自動の Dismiss と m 日の経過による削除（ポップオーバーを開いている間は保留し、`popover_closed` で、開いていないときは期限の時点で行う）、復帰の契機の 4 種類の行、Dismiss している間に生成する行の制限、Mute の判定（カードの `muted` の理由の配列と行の `muted`）、行の 20 件の保持と削除した行の鍵、`older_rows`。List がオフの間に記録した行は、自動の Dismiss の例外、復帰の契機、Review への自動の追加に数えない（生成した時点の List で決める）。20 件の上限と `+ N more` は今の List に従い、今 List がオフの種類の行を数えない。今 List がオフの種類の行は、それらの行の中で PR ごとに 20 件までを保持する。`older_rows` は今の List に従わず、その PR の行を削除したことがあるかを示す（「表の適用」「カードの中の行」）
- disabled の owner の PR と読めなくなった PR：配置、Mute、Dismiss の状態を保ち、n 日と m 日を数え続ける。Dismissed の一覧とその数から除き、`place`、`dismiss`、`restore` は `not_found` にする（「カードの表示と監視」「ワイヤ形式」の `place` の段落）
- レビュー待ち：PR ごとに保存する最新の依頼の時刻で判定する。この時刻は、行を生成しない場合（List がオフ、Dismiss している PR、行の削除のあと）も REVIEW_REQUESTED_EVENT から更新する。自分が作成した PR はレビュー待ちにしない（「レビュー待ちの定義」）。今の `latest_request_row`（engine.rs）による行からの判定を置き換える

## 危険な箇所と確認すること

- **ドラッグ＆ドロップ**：今のアプリに一覧の中のドラッグ＆ドロップはない（`PopoverView.swift` に `onDrag`、`onDrop`、`draggable`、`dropDestination` の使用がない）。NSPopover と NSPanel の中の SwiftUI の一覧で、つまみ ⋮⋮ から始めるドラッグ、区画の間の移動（Review）、スクロールが必要な長さの一覧を確かめる。ドロップできる位置と、Mute の対象のカード、区画の見出し、折りたたんだ区画、`+ N more PRs` の行の上にドロップしたときの配置、Mute の対象のカードをドラッグできないことは「押したときの動作」に従う。ドロップの位置は `place` の `before` または `at` に変換し、先行反映と失敗時の復帰の両方を確かめる。SwiftUI と AppKit の API の動作は記憶で決めず、Apple のドキュメントと試作で確認し、確認方法を完了報告に記載する
- **文字の選択とクリックの選択の両立**：今のカードと行は `pressable`（`onTapGesture` と 2 回のタップの `simultaneousGesture`、右クリックを受ける `RightClickArea`）でクリックを受ける。0.4 では、クリックはカードまたは行の選択、ダブルクリックは単語の選択、ドラッグは範囲の選択で、選択した文字は ⌘C と右クリックの `Copy` でコピーする。⌘C は文字の選択がなければリンクをコピーする。文字の選択は別の項目の選択とポップオーバーを閉じたときに解除する（「押したときの動作」「キーボード」）。SwiftUI の文字の選択がタップのジェスチャー、右クリックのメニュー、つまみのドラッグ、キーの監視（`Surfaces.swift` の `keyMonitor`）と競合しないかは試作で確かめる
- **試作の進め方**：段階 2 の最初に、ドラッグ＆ドロップと文字の選択を同じカードに組み込んだ小さな試作を作成する。試作で示すことは次のとおりである。ドラッグと文字の選択がクリックの選択、右クリック、キーと競合しないこと。アプリが、文字が選択されているかを読み取れること（右クリックの `Copy` を選択があるときだけ表示し、⌘C を選択の有無で分岐するため）。アプリが、文字の選択をコードから解除できること（別の項目を選んだときに解除するため）。SwiftUI の文字の選択でこの 2 つができなければ、AppKit のテキストビューを代わりに使用し、どちらを使用したかを報告する。すべてを満たせば、所有者の確認を待たずに本体の実装に進み、結果を完了報告に記載する。両立できない場合だけ実装を止めてオーケストレーターに報告し、オーケストレーターが所有者に相談する
- **閉じた PR の発見と Dismiss の記録**：閉じた PR の検索は、ブランチの削除やラベルの変更でも更新時刻が進む PR を返す。表示または復帰の契機は行の生成だけで、更新時刻ではない（「API の使い分け」の最後の項目）。知らない閉じた PR を、行を生成しないまま保存しないこと、記録だけが残る PR を記録した `updatedAt` より進んでいないときに取得しないこと、開いている PR だけに記録を残すこと、owner とアカウントの削除で記録を消すことを確かめる。Dismiss している間にマージされた PR を Restore または復帰させたときの検知、`Done` の中の位置、n 日の起点も確かめる（「Dismiss」の復帰の契機の項目）
- **Checks の前回の確定した結果**：前回の観測値（`pending` を含む）と前回の確定した結果を別に保存すること、head のコミットの変化で同じ `failed` を新しい確定として扱うこと、`passed` が続く間は行を生成しないこと、Mergeable の行と同じ取得では Checks passed を生成しないこと、行を生成しない 3 つの時点を確かめる。DESIGN.md「状態変化の行」の第 2 段落の場面（実行中で検出して成功、成功で検出、失敗のあとの成功、修正のプッシュのあとの再度の失敗、取得の間に実行中を観測できなかった場合）を表形式のテストにする
- **要求ごとの成否**：分割の再帰が 1 件で止まること、成功した要求の結果が反映されること、失敗した要求だけを再実行すること、通常の取得の時刻にすべての要求に戻ること、owner の成功の時刻が「最初の取得を開始した時刻」になること、5 分の帯と Updated が要求の失敗の残りで決まることを、偽の GitHub と偽の時計で確かめる
- **先行反映**：デーモンが失敗を返したとき（接続できない場合を含む）の復帰、帯の文言と 10 秒、続く操作による帯の消去、先行反映のあとに受信した `account_changed` の再取得との整合（選択とドラッグ中の位置を保つこと）
- **テストの隔離**：テストは実際の Keychain、ネットワーク、状態ディレクトリ、ホーム、通知センター、ログイン項目、標準の UserDefaults に触れない。既定のビルドのテストは Keychain とネットワークに触れず、`dev-ingest` ビルドだけが偽の Keychain（`SHIIBAR_GH_DEV_KEYCHAIN`）と偽の GitHub（ループバックの URL）を使用する（M2〜M5 と同じ）。移行のテストでアカウントのある DB を開くと、デーモンが Keychain を読み込む点に注意する
